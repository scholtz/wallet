## 3. Findings

### AW-2026-074 — The "had a wallet" flag cookie is origin-wide, script-readable and sent to the server — **Low** — New
- **Files:** `src/scripts/storagePersistence.ts` (`setHadWalletMarker`, `hasHadWalletMarker`, `clearHadWalletMarker`), `src/store/wallet.ts` (`markWalletUsed`, `destroyWallet`), `src/components/{Login,NewWallet}.vue`.
- **Description:** On every wallet open/create/import the app sets `awallet_had_wallet=1; max-age=31536000; path=/; SameSite=Strict` (+`Secure` on https). It is the only signal that survives a browser's origin-wide storage eviction, which is the design goal. Properties of a cookie that differ from the rest of the app's storage: it is not `HttpOnly` (any script on the origin reads or clears it), it is sent in the `Cookie` header with every request to the origin (so the server, CDN and any proxy learn that this browser holds a wallet), and with `path=/` it is shared by every application on the same host. `hasHadWalletMarker` is also trusted for a user-facing message ("The browser has probably deleted its site data. Create a new wallet or import your backup.").
- **Attacker precondition:** A party that can read request headers for the origin (the hosting provider, a shared-host neighbour) or that can run script on the same host (another site on a shared `github.io`-style origin). No key material is involved.
- **Impact:** Disclosure that a browser has used a wallet (a weak targeting signal, comparable to the visible fact that the site is installed). A script on the host can set the cookie to show a false "your data was deleted" notice on an empty browser, or clear it to suppress the real one. No funds, keys or wallet names are exposed; the cookie holds only `1`. The FAQ (`faq.categories.privacy.a2`, all 10 locales) now discloses the cookie accurately.
- **Recommendation:** Accepting this is reasonable; if it is kept, (a) scope the cookie to a path the app owns when deployed under a sub-path, and (b) say in the notice that the cause is "probable", which it already does. A cookie-free alternative does not exist because the point is to outlive IndexedDB/localStorage eviction.

### AW-2026-075 — Swap balance refresh: displayed and clamped amounts rest on the configured indexer; execute has no re-entrancy guard — **Informational** — New
- **Files:** `src/composables/useSwap.ts` (`executeAndRefresh`, `refreshBalance`, `makeAssets`), `src/pages/Swap.vue` (`autoRefreshBalance`), `src/scripts/swap/refreshBalance.ts`.
- **Description:** The page now re-reads the account every 30 s and after a swap. The numbers it shows, and the `payamount` it clamps to `maxAmount` when the form is untouched, come from the configured indexer, which is unauthenticated (AW-2026-010/011). `executeAndRefresh` sets `settlingSwap` before the first await, which disables every execute button through `allowExecute*`, but it has no early `if (settlingSwap.value) return` of its own, so a non-UI second call would run the aggregator twice (the Biatec aggregator fetches a fresh route on each call).
- **Traced:** a hostile indexer can already show any balance on every other page, and the amount that is signed is the one in the aggregator's own transactions, validated by `assertSwapTransactionsSafe` (AW-2026-043), not the clamped field. The buttons are the only caller of the `click*` functions and are disabled synchronously with `settlingSwap`. After a send, `waitForConfirmation` swallows its own errors (`store/algod.ts:567-580`) and each aggregator `execute` catches its own, so `executeAndRefresh` always reaches `settleAfterSwap` and the spent quote is cleared (`clearQuotes`).
- **Impact:** None today; recorded so the dependence on the indexer and the guard-by-button pattern are visible.
- **Recommendation:** Add `if (settlingSwap.value) return;` at the top of `executeAndRefresh`.
