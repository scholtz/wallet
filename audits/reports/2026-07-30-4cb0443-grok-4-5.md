## Executive summary

This audit covers the ~28 feature/fix commits on `master` since the prior report (`6f2b077..4cb0443`), dominated by transaction **simulation-before-sign**, **ARC-56** app-call decoding, **ARC-14** auth UX, swap-route simulation, genesis/CAIP-10 hash handling, and CI/CD/K8s deploy work. No Critical findings. No new High findings that enable remote fund theft by themselves.

**Prior Medium AW-2026-037 (FAQ `v-html`) is confirmed Closed** at HEAD: answers render via `<i18n-t>` with hardcoded-URL named slots; locale strings no longer embed HTML. **AW-2026-038** is **Closed as intentional design**, not as “auto-init restored”: `App.vue` still has no WC bootstrap, and `CLAUDE.md` now explicitly requires WC init only after user intent — correcting the prior registry note that claimed an uncommitted restore of always-on init.

**Counts this audit:** New open: 1 Medium, 3 Low. Closed/reclassified since last registry: AW-2026-037 verified Closed; AW-2026-038 Closed (by design). Open technical (excl. Accepted user-behavior): 15 including new. Accepted external risks AW-2026-029..034 unchanged.

## Findings

### AW-2026-039 — Pre-sign simulation treats configured algod as oracle; UI language can over-assert “actual” outcome

- **Severity:** Medium  
- **Status:** New  
- **Affected files:**  
  - [`src/store/algod.ts`](src/store/algod.ts) (`simulateTransactionGroups`, ~L358–L378)  
  - [`src/components/TransactionGroupSimulation.vue`](src/components/TransactionGroupSimulation.vue) (~L308–L365, disclaimer ~L136–L137)  
  - [`src/components/ConnectRequestsTable.vue`](src/components/ConnectRequestsTable.vue), [`src/pages/SignAll.vue`](src/pages/SignAll.vue) (embed the panel)  
  - Locale copy: `connect.simulation_success`, `swap.simulation_sent` / `simulation_received` (“You would actually pay/receive”) in [`src/locales/en.json`](src/locales/en.json)  
- **Description:** Since `6f2b077`, signing surfaces (WC batch table, SignAll, swap routes) dry-run the **exact unsigned transactions** via `algod.simulateTransactions` with `allowEmptySignatures` / `fixSigners: true`. This is a genuine UX improvement and the panel includes disclaimers (`connect.simulation_disclaimer`, `connect.simulation_defi_disclaimer`). However:

  1. Simulation always uses the **user-configured** algod client (`createAlgodClient(rootState)`), the same trust base already flagged in AW-2026-010/011.  
  2. A malicious or MITM’d node can return an arbitrary `SimulateResponse` (success + fabricated asset/state deltas) while the wallet still signs the real local txn bytes.  
  3. UI copy such as “Simulation succeeded - no errors” and swap strings “You would **actually** pay/receive” over-assert certainty relative to that trust model. The signed payload is still shown in the detail tables (rekey/close-to warnings remain), so this is **misleading-preview**, not silent wrong-bytes signing — but wallet UX that misrepresents outcome is an in-scope vulnerability class per audit instructions §1.9.

  Unsigned txn intent (addresses, amounts, app calls) is also **exfiltrated to whatever node is configured** before the user signs — expected for simulation, and a privacy cost if the endpoint is hostile.

- **Attacker precondition:** Control or MITM of the configured algod endpoint, **or** compromise of the unpinned public-node list that auto-selects endpoints (AW-2026-011), **or** user already pointed Settings at a malicious URL (AW-2026-010). Not exploitable against a honest public node with no user misconfig.  
- **Impact:** User approves a harmful group because the green simulation panel showed benign net asset/state changes. Does not by itself change signature bytes; compounds endpoint-trust findings. Privacy leak of pre-sign intent to the node operator.  
- **Recommendation:**  
  1. Soften absolute copy (“actually”, unqualified “succeeded”) to “node-reported preview” language; keep/strengthen the existing DeFi disclaimer.  
  2. Visually separate **cryptographic txn fields** (from local decode) from **node-reported simulation** (badge: “from &lt;algod host&gt;”).  
  3. When genesis cross-check (AW-2026-005) fails or public-node list is used without pin, show an elevated warning on the simulation panel.  
  4. Optionally allow disabling auto-simulate, or require explicit “Run simulation” so intent is not always POSTed to the node on open.

### AW-2026-040 — Hardcoded shared Deflex API key in client source

- **Severity:** Low  
- **Status:** New  
- **Affected files:** [`src/scripts/aggregators/deflex.ts`](src/scripts/aggregators/deflex.ts) L5, L47–L67  
- **Description:**

```typescript
const DEFAULT_DEFLEX_API_KEY = "1b72df7e-1131-4449-8ce1-29b79dd3f51e";
// ...
const apiKey = context.$store.state.config.deflex.trim() || DEFAULT_DEFLEX_API_KEY;
// apiKey embedded in fetchQuote query string and fetchExecuteSwapTxns JSON body
```

  Every user without a custom Settings key shares one published credential. Swap quotes send account address, asset IDs, amounts, and slippage to `deflex.txnlab.dev` under that key.

- **Attacker precondition:** Anyone reading the public repo or network traffic; Deflex operator; shared-key abuse (quota exhaustion).  
- **Impact:** No direct key-material or signing compromise. Cross-user correlation of swap activity under one API key; shared quota/DoS against Deflex for all default users; key cannot be considered secret.  
- **Recommendation:** Rotate the published key; treat default as “anonymous/public” in docs; prefer user-supplied keys; avoid putting the key in query strings (use header if API allows); rate-limit/backoff UX when Deflex rejects the key.

### AW-2026-041 — ARC-56 registry fetched without integrity pinning (display-metadata trust)

- **Severity:** Low  
- **Status:** New  
- **Affected files:** [`src/scripts/arc56/registry.ts`](src/scripts/arc56/registry.ts) L19–L49, consumers in [`Arc56CallDetails.vue`](src/components/Arc56CallDetails.vue), [`TransactionGroupSimulation.vue`](src/components/TransactionGroupSimulation.vue)  
- **Description:** Contract ABI/method labels are loaded via unauthenticated `fetch` against, in order: same-origin `/arc56-registry`, `https://scholtz.github.io/ARC56Registry`, then raw GitHub content. No SRI, signature, or hash pin of the JSON. Lookups are keyed by **on-chain program hash** (good — wrong program cannot get a matching honest registry entry), but a MITM on the HTTPS path or compromise of the GitHub Pages/raw content can return a **forged ARC-56 JSON for a real program hash**, mislabeling method names, argument meanings, and human-readable state keys in the signing UI.

- **Attacker precondition:** MITM of registry transport, or write access to the published registry content the wallet falls back to.  
- **Impact:** Display-only confusion (user thinks they call `optIn` while raw selector is something else). **Signed bytes remain the undecoded app-call**; ARC-56 is not in the signature path. Severity Low because exploitation needs network/content compromise and still must pass user review of raw fields if they expand details — but it weakens the new “understandable app call” trust cue.  
- **Recommendation:** Pin registry content (commit SHA / checksum map shipped with the app, or signed manifest); show “unverified metadata” when falling back to network; never hide raw selector/app index when metadata is present.

### AW-2026-042 — Remaining external links missing `rel="noopener noreferrer"`

- **Severity:** Low  
- **Status:** New (residual of AW-2026-013 class)  
- **Affected files:**  
  - [`src/components/Login.vue`](src/components/Login.vue) ~L139–L142 (`target="_blank"`, no `rel`)  
  - [`src/components/NewWallet.vue`](src/components/NewWallet.vue) ~L73–L76 (same GitHub translate wiki link)  
  - [`src/pages/Account/ScheduledPayments.vue`](src/pages/Account/ScheduledPayments.vue) ~L641–L645 (xGov proposal link)  
- **Description:** WC peer links and FAQ/Arc56 explorer links correctly use `rel="noopener noreferrer"`. A few leftover `target="_blank"` anchors do not. (`Donation.vue` / `PaymentGateway.vue` use `rel="noreferrer"` only — modern HTML treats `noreferrer` as implying `noopener`; still prefer the explicit pair for clarity.) Settings backup `download` data-URL is not an external navigation risk.

- **Attacker precondition:** Compromise or hostile content on the opened origin (e.g. GitHub wiki edit, linked doc host) plus a user click from AWallet.  
- **Impact:** Classic reverse tabnabbing → opener navigated to phishing wallet UI while user focuses the new tab. Lower likelihood than DApp/session issues; defense-in-depth.  
- **Recommendation:** Add `rel="noopener noreferrer"` to every `target="_blank"`; add a simple lint/CI grep that fails on `target="_blank"` without `noopener`.

### AW-2026-038 — WC not auto-initialized — **Closed (intentional design)**

Prior registry text claimed an uncommitted restore of `App.vue` `initWc()` bootstrap. **That restore is not present at `4cb0443`.** [`src/App.vue`](src/App.vue) has no `wc/init` dispatch; the only user-facing init remains [`Connect.vue`](src/pages/Connect.vue) “Init WC” (`dispatch("wc/init")`). [`CLAUDE.md`](CLAUDE.md) now states:

> Make sure the Wallet Connect is not initialized on page refresh, only after user on intention enables it. This prevent fraudlent transactions to be received when user does not expect it.

Reclassification: not a latent regression to “fix by always listening,” but an **accepted product/security tradeoff** (reduced unsolicited `session_request` surface at the cost of deaf approved sessions until manual init). Residual product risk (silent unpaired listening) should be mitigated in UX (badge: “WC not listening”) rather than by silently reverting the threat-model choice. Status **Closed** with design rationale — do not re-open solely because auto-init is absent.

Self-built payments still refuse mismatched genesis id/hash. Mitigation quality improved; residual trust in `publicData` genesis list (AW-2026-011) remains.
