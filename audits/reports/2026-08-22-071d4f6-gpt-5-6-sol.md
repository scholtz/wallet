## Executive summary

This audit reviewed commit `071d4f6`, including the security remediation for the prior DEX and ARC-60 findings, new Falcon-1024 post-quantum accounts, usage-based transaction fees, network-aware explorer and Biatec Scan integrations, WalletConnect lifecycle changes, and deployment updates. One new **Medium** finding was identified: ARC-60 AUTH requests can contain arbitrary or non-JSON bytes, and the wallet will let the user sign them while showing only opaque base64; the draft ARC-60 specification requires AUTH data to be JSON and all signed data plus authenticator data to be shown in human-readable form.

The prior Critical DEX finding is materially improved but not closed. The new validator rejects foreign senders, rekey, and close-out fields, yet still signs an ordinary payment or asset transfer of any amount to any receiver. On Biatec's execute-time re-fetch, the output check trusts a number supplied by the same potentially compromised router, so a malicious response can still drain spendable funds without using a close or rekey field. The prior High ARC-60 domain finding is also improved but not closed: the requested domain is compared to WalletConnect peer metadata, but that metadata is DApp-supplied; the request event's independent `verifyContext` is available and ignored.

AW-2026-046 is confirmed fixed by enforcing the session's approved account list at the signing choke point. AW-2026-047 is closed as a non-defect after checking the current ARC-60 specification, which explicitly mandates `EdDSA(SHA256(data) + SHA256(authenticatorData))`. No Critical or High finding is newly introduced by this revision. There are **19 non-closed technical risks** in the cumulative registry after this audit: 12 Open and 7 Mitigated, excluding six Accepted user/environment risks.

## Findings

### AW-2026-043 - DEX validation still permits unbounded ordinary transfers supplied by an aggregator

- **Severity:** Critical
- **Status:** Mitigated (carried forward; not closed)
- **Affected files:**
  - `src/scripts/aggregators/validate.ts` lines 11-35
  - `src/scripts/aggregators/biatec.ts` lines 237-251
  - `src/scripts/aggregators/folks.ts` lines 139-149
  - `src/scripts/aggregators/deflex.ts` lines 160-164

#### Description

Commit `0b3947e` added `assertSwapTransactionSafe` and invokes it before each raw-key signing operation. It correctly rejects:

- A sender other than the connected account.
- Any `rekeyTo`.
- Payment `closeRemainderTo`.
- Asset-transfer `closeRemainderTo`.

This closes the easiest account-close and takeover payloads identified in the prior report. It does not validate payment or asset-transfer receiver, asset ID, amount, fee, application ID, application arguments, group composition, or the group's net economic effect against the user's approved quote.

A compromised aggregator therefore does not need a close or rekey field. It can return an ordinary payment from the expected sender to an attacker for the account's spendable ALGO balance, or an ordinary asset transfer for the user's full holding. The transaction passes all four checks and is signed directly with `senderSK`. Biatec is especially exposed because it fetches a new transaction group only after the user approved the preview; Deflex and Folks reuse quote-time transactions, which gives their simulation display some additional mitigation but is not an enforceable client-side authorization bound.

The current helper protects transaction shape, not transaction intent. The prior finding's complete-loss impact remains possible.

#### Attacker precondition

Control or compromise of an enabled aggregator API or its trusted delivery path, followed by a user performing the normal Get Quote and Execute flow. For Deflex/Folks, misleading the quote-time simulation or relying on the user not detecting the unexpected net debit is additionally required. For Biatec, the execute-time response is not re-simulated or re-confirmed.

#### Impact

Loss of the swapping account's spendable ALGO or selected ASA through a syntactically ordinary transfer. A malicious application call may also be signed if its sender matches and it does not use the three rejected fields.

#### Recommendation

Decode the complete group and enforce its net effects before signing. At minimum:

1. Cap the user's net debit of the selected input asset to the approved `payamount` plus a narrowly bounded fee.
2. Require the user's net receipt of the selected output asset to meet the approved slippage-adjusted minimum, computed from decoded transactions or an independently simulated execute-time group rather than an API response field.
3. Reject unrelated payment/asset IDs and unexpected application calls, or match the group against an allowlisted route plan produced by the selected integration.
4. Bind user approval to a hash of the exact unsigned transaction bytes and refuse to sign any different group.
5. Prefer the central signer abstraction over distributing raw `sk` access to integrations.

The residual five-year misuse probability is reduced from Medium (~15%) to **Low (~8%)** because several high-impact fields are now blocked, but API compromise still has a direct ordinary-transfer drain path.

### AW-2026-044 - ARC-60 domain binding relies on spoofable WalletConnect peer metadata

- **Severity:** High
- **Status:** Mitigated (carried forward; not closed)
- **Affected files:**
  - `src/scripts/encoding/arc60.ts` lines 106-128
  - `src/store/signer.ts` lines 535-550
  - `src/store/wc.ts` lines 772-786
  - `src/components/ConnectSignDataRequestsTable.vue` lines 65-83 and 138-145
  - `node_modules/@walletconnect/types/dist/types/sign-client/client.d.ts` lines 31-39 (event contract)

#### Description

The remediation adds an important second check: `domainMatchesSessionOrigin` compares the DApp-requested domain to the hostname in `session.peer.metadata.url`, and the signer rejects mismatches. The UI also shows the session peer name and URL next to the requested domain.

This prevents one request within an established session from silently changing to a domain different from that session's recorded metadata. It does not establish that the metadata URL is the DApp's real web origin. WalletConnect peer metadata is supplied by the peer during session establishment. A malicious DApp can set its metadata URL to `https://victim.example`, then request an ARC-60 signature for `victim.example` with matching authenticator data. The request, metadata comparison, and UI all agree on the attacker-chosen lie.

WalletConnect 2.23.10 provides `verifyContext` directly on every `session_request` event. The current event handler receives the full event but never stores or checks `sessionRequest.verifyContext`; only session-proposal verification is surfaced elsewhere. The independent signal that could distinguish validated origin, mismatch, unknown, or scam is therefore discarded on the high-impact arbitrary-signing path.

#### Attacker precondition

A malicious DApp obtains a WalletConnect session while advertising spoofed peer metadata, then asks the user to approve an ARC-60 AUTH signature. The user sees a consistent but attacker-controlled domain and connected-app URL.

#### Impact

The attacker can obtain an account signature asserting authentication to another domain. A relying party that accepts the ARC-60 proof may authenticate the attacker as the wallet owner, causing third-party account takeover. Direct on-chain transfer is not performed by ARC-60 itself.

#### Recommendation

Persist `sessionRequest.verifyContext` with each sign-data request and enforce it at signing time. Refuse ARC-60 AUTH signing when verification reports `INVALID` or `SCAM`; require an explicit high-friction warning for `UNKNOWN`, and compare a `VALID` verified origin to the requested domain. Keep the peer-metadata comparison as defense in depth, but do not label it as an actual origin. Show both the verified origin/status and peer-claimed metadata in the review UI.

The residual five-year misuse probability is **Medium (~15%)**, reduced from ~20% because cross-request metadata changes are blocked and the peer identity is displayed, but malicious initial metadata remains straightforward.

### AW-2026-045 - Biatec execute-time route remains different from the preview and is checked using server-claimed output

- **Severity:** Medium
- **Status:** Mitigated (carried forward; not closed)
- **Affected files:**
  - `src/scripts/aggregators/biatec.ts` lines 169-223 and 237-251
  - `src/composables/useSwap.ts` quote-time `simulateAggregatorQuote`

#### Description

Biatec still obtains one route for quote-time simulation and a second route in `execute()`. The remediation passes the slippage-adjusted `receiveMinimum` to the second API request and aborts if `route.route.outputAmount` is below that minimum.

That check catches an honest router returning an explicitly worse advertised route. It does not bind the preview to the signed bytes and does not independently establish the executed output: both `outputAmount` and `txsToSign` come from the same API response. A compromised router can report an acceptable `outputAmount` while returning unrelated or economically harmful transactions. AW-2026-043's shape validator will reject close/rekey/foreign-sender payloads but not an excessive ordinary transfer.

#### Attacker precondition

Control or compromise of the Biatec Router API or delivery path. Ordinary market movement can also make the second group differ from the preview without malicious behavior, though the minimum request reduces user loss from that benign case.

#### Impact

The user approves a simulation of one transaction group while the wallet signs another. Combined with AW-2026-043, the later group may debit more than the user approved even while the server claims an acceptable output.

#### Recommendation

Either reuse the exact group that was simulated and approved, or simulate the execute-time group and require fresh confirmation. Compare decoded/simulated net debits and credits against the approved input and minimum output. Bind approval to a digest of the exact unsigned group.

Residual five-year misuse probability is **Low (~8%)**, reduced from ~10% by the new slippage minimum but not eliminated.

### AW-2026-048 - ARC-60 AUTH accepts and signs opaque, non-JSON data without a human-readable review

- **Severity:** Medium
- **Status:** New
- **Affected files:**
  - `src/scripts/encoding/arc60.ts` lines 154-179
  - `src/store/wc.ts` lines 360-393
  - `src/components/ConnectSignDataRequestsTable.vue` lines 86-104

#### Description

`decodeArc60Request` validates scope, presence of domain/authenticator data, and base64 decoding, but it does not parse `data` as JSON or enforce the declared encoding. For AUTH scope, the current draft ARC-60 specification says the data **MUST** be a JSON object, defines `ERROR_BAD_JSON`, and requires the signed data to be presented in human-readable form.

The event handler decodes the bytes as UTF-8 and sets `dataText` whenever the result contains printable characters. It does not require valid JSON or validate a schema. If the bytes are non-printable, the review UI omits the text and shows only the original base64. The UI also does not display `authenticatorData` or how its domain hash was calculated, despite ARC-60's Security Considerations requiring both to be shown.

The signing action hashes and signs these bytes without further content validation. A malicious DApp can therefore ask the user to sign an opaque payload whose meaning cannot reasonably be assessed from the displayed base64. This is a transaction-intent/UI-integrity issue: cryptography is correct, but informed consent is not.

The optional `hdPath` is also accepted and stored without validation or display. The current signer derives according to the wallet account's stored HD index rather than the supplied path. That behavior avoids arbitrary attacker-selected derivation, but it does not satisfy the specification's requirement to validate a supplied BIP44 path and can mislead interoperating DApps about which key signed.

#### Attacker precondition

A DApp with an approved WalletConnect session sends an `algo_signData` AUTH request containing non-JSON or opaque base64 data, and the user clicks Sign despite being unable to inspect a human-readable message.

#### Impact

The user may produce a valid authentication signature over content they could not understand or compare with the DApp's stated action. Depending on the relying protocol, that signature can authorize an unintended login, challenge, delegation, or other off-chain action. This finding compounds AW-2026-044 but does not itself move on-chain funds.

#### Recommendation

For AUTH scope:

1. Decode UTF-8 strictly, parse JSON, reject non-JSON with `ERROR_BAD_JSON`, and reject unsupported `encoding` values.
2. Render the parsed object in a stable human-readable representation that makes all fields visible; do not enable Sign when only opaque base64 is available.
3. Display `authenticatorData`, the requested domain, and the computed/verified domain hash.
4. Validate supported `hdPath` values against the selected account's real derivation path, or reject requests that supply a path until path-based signing is implemented.
5. Add negative unit tests for malformed base64, invalid UTF-8, non-JSON AUTH data, hidden/control characters, unsupported encodings, and invalid HD paths.

Estimated five-year misuse probability: **Medium (~12%)**. Malicious sign-in challenges are a realistic DApp attack surface, but exploitation still requires explicit user approval and a relying service that gives the resulting signature value.

## Resolved since last audit

### AW-2026-046 - ARC-60 signing not scoped to session-approved accounts

**Status: Fixed since last audit.** `wc/signSignDataItem` extracts addresses from `session.namespaces.algorand.accounts`, passes them into `signer/signArc60Data`, and the signer rejects any requested account not in that list before computing or signing the digest (`src/store/signer.ts` lines 550-558). This check is at the signing choke point rather than only in the UI. The general WalletConnect transaction namespace issue remains separately tracked as AW-2026-016.

### AW-2026-047 - ARC-60 digest has no additional protocol tag

**Status: Fixed since last audit (closed as verified non-defect).** The current ARC-60 draft explicitly specifies the AUTH signature as `EdDSA(SHA256(data) + SHA256(authenticatorData))`. The implementation matches that construction. Adding a private prefix would break interoperability rather than improve conformance. The general observation that one key signs multiple protocol payloads remains useful design context but is not a vulnerability in this implementation.

## Falcon-1024 review

No new finding was raised for the Falcon implementation.

- A fresh 32-byte seed is generated with `crypto.getRandomValues`, converted to a checksum-valid 25-word Algorand mnemonic, and domain-separated through `pq25WordMnemonicToSeed(..., FALCON_1024_SCHEME)`.
- Falcon key generation is deterministic. The mnemonic, public key, and cached private key are stored in the same wallet account object that is encrypted by the existing PBKDF2/AES-GCM wallet-at-rest layer.
- Export is password-gated and the developer JSON view redacts both mnemonic and private key.
- Rekey resolution selects the actual signer account before dispatching `signByFalcon`.
- `addressWithSignersFromRawFalcon1024Signer` receives the SDK's `bytesToSign` callback input and emits a `pqsig` signed-transaction envelope. The unit test independently verifies the public-key-derived address and Falcon signature over `tx.bytesToSign()`.
- Usage-based fee estimation adds the Falcon signature surcharge even when unsigned simulation cannot infer the signature scheme, and a 0.1 ALGO client cap prevents silent node-directed fee escalation.
- `falcon-1024@0.2.0` has no install/preinstall/postinstall script and no reported advisory. It is still a young, security-critical WASM dependency; pinning its integrity through the lockfile and monitoring upstream releases remains important supply-chain hygiene.

Residual validation gap: no live network submission of a Falcon transaction was performed during this audit, so consensus acceptance and fee behavior were established from SDK integration and unit tests rather than end-to-end chain confirmation.
