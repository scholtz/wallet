## 1. Executive summary

This audit covers the 53 commits since `071d4f6`: the new **Liquid Auth** dApp transport (passkey-linked WebRTC), a Folks Finance USDC↔fUSDC conversion flow, asset opt-out, an ARC-56 risk-scoring icon, Ledger refactors, a multisig WalletConnect fix, a Cypress→Playwright migration and a large dependency refresh. Ten new findings are raised: **1 High, 6 Medium, 3 Low**. The High finding (AW-2026-049) is a path to fund loss: when linking an account via Liquid Auth, the wallet signs a service-supplied "challenge" with the raw account key, with no check on the service origin and no rejection of Algorand signing prefixes. A hostile `liquid://` link can therefore obtain a valid transaction signature. It requires the user to paste/scan the link and approve a passkey prompt. It should be fixed before Liquid Auth is promoted beyond the stage environment. No prior Critical/High row regressed; the Critical AW-2026-043 remains Mitigated with its ordinary-transfer residual. Dependency exposure improved (`pnpm audit --prod`: 8 advisories, down from 18).

Findings by severity (new): Critical 0, High 1, Medium 6, Low 3. Total non-Closed, non-Accepted rows after this audit: see registry.

## 3. Findings

### AW-2026-049 — Liquid Auth signs a service-supplied challenge raw, from an unvetted origin — **High** — New
- **Files:** `src/store/signer.ts:649-686` (`signLiquidChallenge`), `src/scripts/encoding/arc60.ts:181-183` (`signArc60DigestWithSk` = bare `nacl.sign.detached`), `src/scripts/liquid/webauthn.ts:134-173`, `src/scripts/liquid/protocol.ts:180-193` (`parseLiquidDeepLink`), `src/store/liquid.ts:271,311-321`, `src/pages/Connect.vue:~896-905`.
- **Description:** The service origin comes from the pasted/scanned `liquid://<host>?requestId=…` link; no code enforces an allowlist or same-registrable-domain (only `docs/LIQUID_AUTH.md` says it "must be"). The wallet POSTs `/attestation/request` to that host, takes `options.challenge`, and signs those bytes unmodified with the account's ed25519 key (HD path: `signArc60DigestWithHd` with `HdEncoding.NONE`). No length check, no domain separation, no rejection of `TX`/`MX`/`Program`/`ProgData` prefixes. Nothing is displayed beyond the browser's passkey prompt.
- **Precondition:** User pastes/scans an attacker link, selects an sk/HD account, approves the passkey prompt.
- **Impact:** Attacker sets `challenge = "TX" || msgpack(txn)` (close-out, full-balance payment, rekey) and receives a valid transaction signature in the Liquid extension result, then broadcasts it. Same technique works for LogicSig prefixes. Bypasses every review table.
- **Recommendation:** (1) Allowlist/validate the service origin (https, expected host, no IP/port) before any fetch. (2) In `signLiquidChallenge` require a fixed-length nonce (e.g. 32 bytes) and reject Algorand signing prefixes. (3) Prefer a domain-separated signed payload if the Liquid spec permits. (4) Show the target host and an explicit warning before the passkey prompt.

### AW-2026-050 — Liquid peer identity and origin are unauthenticated / self-declared — **Medium** — New
- **Files:** `src/store/liquid.ts:389-396,544-557`, `src/scripts/encoding/arc60.ts:118-129`, `src/shared/liquid.ts:84-105,259-291`, `docs/LIQUID_AUTH.md`.
- **Description:** For Liquid, `sessionOrigin` is `session.peer.url`, taken from the dApp's own `hello` message, so the AW-2026-044 domain-binding check is circular. Signaling accepts the first `answer-description` with no authentication of the answerer; `requestId` acts as a bearer room id. A malicious/compromised service (see 049) can substitute itself for the dApp. (A sub-auditor rated the domain-check aspect High; rated Medium here because the ARC-60 digest `SHA256(data)||SHA256(authData)` cannot be converted to a transaction signature and a user click is still required.)
- **Impact:** Spoofed app identity displayed to the user; AUTH-scope signatures for a victim domain; request spam. Whether the stock liquid-auth server restricts room membership is **Needs verification**.
- **Recommendation:** Label peer metadata "claimed, unverified"; show the Liquid service origin as the trusted identity; add a pairing confirmation code; or block ARC-60 AUTH over Liquid until origin is bound.

### AW-2026-051 — Transaction sign requests not scoped to the session's approved accounts (WalletConnect and Liquid) — **Medium** — New (Liquid confirmed; WalletConnect Needs verification)
- **Files:** `src/store/liquid.ts:410-435`, `src/store/wc.ts:~284-345`, `src/components/ConnectRequestsTable.vue:~744-775`, `src/shared/decodeSignRequests.ts:137-152`.
- **Description:** Only the ARC-60 path enforces approved accounts (AW-2026-046). A peer paired for account A can submit transactions whose sender is any other wallet account; they appear in the same review table. Additionally the summary `from` field is always empty (`decoded.from` never populated); the table uses `txn.sender`, so display is correct but context is thinner than it appears.
- **Impact:** User must click Sign and sees the sender; risk is user confusion/decoy, not silent signing.
- **Recommendation:** Reject requests whose sender (or auth address) is not in the session's approved accounts (error 4100); fix `from` extraction to `decoded.sender`.

### AW-2026-052 — No bounds or rate-limiting on unauthenticated Liquid peer input — **Medium** — New
- **Files:** `src/scripts/liquid/protocol.ts:224-231`, `src/shared/liquid.ts:214-216`, `src/store/liquid.ts:200-202,413-421`.
- **Description:** CBOR decode has no length/depth cap; whole `txns` array decoded synchronously; `addRequest` unbounded; one malformed entry throws inside `handleMessage` → unhandled rejection with no error reply. Request flooding can bury a genuine request. cbor-x prototype-handling **Needs verification**.
- **Recommendation:** Cap payload (~256 KiB), txn count (16), pending requests per session; wrap decode in try/catch and reply 4200; set explicit cbor-x options.

### AW-2026-053 — Folks lend / fUSDC opt-in path skips the genesis cross-check and fee cap — **Medium** — New
- **Files:** `src/components/FolksLendConvert.vue:~244-254`, `src/components/FolksFAssetOptIn.vue:~106-111`, `src/store/algod.ts:245-253`, `src/scripts/folksLend/transactions.ts:144-199`.
- **Description:** These flows use `algod/getTransactionParams` directly, without `assertParamsMatchNetwork` (AW-2026-005 guard used by `preparePayment` and `optOutAsset`) and without a fee cap; `assertFolksLendTxnsSafe` bounds fee only on app calls. `canSubmit` checks the configured env, not the node's genesis.
- **Precondition:** Malicious/custom/poisoned node (AW-2026-010/011) returning an inflated fee or wrong genesis.
- **Impact:** Signing opt-in/deposit transactions with an extreme fee (ALGO loss to proposer) or for the wrong network.
- **Recommendation:** Call `assertParamsMatchNetwork`; enforce a fee cap for every transaction in `assertFolksLendTxnsSafe` (and `assertSwapTransactionSafe`).

### AW-2026-054 — Asset opt-out `assetCloseTo` taken from node response and not shown — **Medium** — New
- **Files:** `src/store/algod.ts:~382-410`, `src/scripts/assets/optOut.ts:9-16`, `src/pages/Account/Assets.vue` (`askOptOut`/`confirmOptOut`).
- **Description:** The close-to target is `getAssetByID().params.creator` from the configured node. The confirmation dialog shows asset name/id and a balance warning, not the target address; no second-source check; `signAndSend` has no simulation. Normal case is safe (balance returns to the creator).
- **Precondition:** Malicious/poisoned node and user confirms opt-out of an asset with a non-zero balance.
- **Impact:** Entire asset balance redirected to an attacker address.
- **Recommendation:** Display the close-to address; verify creator against the indexer; refuse (or require explicit address confirmation) when balance > 0.

### AW-2026-055 — ARC-56 "trusted" verdict rests on unauthenticated inputs — **Medium** — New (compounds AW-2026-041)
- **Files:** `src/scripts/arc56/risk.ts:90-102`, `src/scripts/arc56/riskTxn.ts`, `src/scripts/arc56/decode.ts:~565-575`, `src/composables/useArc56Summaries.ts:36-48`, `src/scripts/arc56/registry.ts`, `src/store/algod.ts:~455-495`.
- **Description:** The approval-program hash is computed from bytes returned by the configured node and matched against registry JSON from mirrors (same-origin, GitHub Pages, raw GitHub) with no integrity pin. A green "trusted" icon appears when the spec matches and any owner is `low` risk. A malicious node can return a trusted app's program for the app id the attacker calls; a tampered mirror can hide bans. `isRiskyTransaction` does not flag an ordinary `pay`/`axfer` placed beside a trusted app call. Mitigations: sensitive calls capped at "warning"; lookup failure fails closed.
- **Recommendation:** Do not show "trusted" on custom/unpinned nodes; cross-check the program hash via a second source; pin/sign registry content; label the verdict advisory.

### AW-2026-056 — Unpinned container images and deploy hardening gaps — **Low** — New
- **Files:** `.github/workflows/awallet-main.yml:~106-113`, `awallet-stable.yml`, `k8s/deployment-liquid-auth-{stage,stable}.yaml`, `.github/workflows/liquid-auth.yml`, `k8s/liquid-auth-secrets.sh`.
- **Description:** ARC-56 registry runs `scholtz2/arc56-registry:latest` and is now restarted on every deploy; Liquid Auth runs `ghcr.io/algorandfoundation/liquid-auth:develop` with `imagePullPolicy: Always` (mutable tags on services feeding AW-2026-055 / passkey binding). Liquid pods lack `securityContext` hardening and NetworkPolicy; `SESSION_SECURE: "false"` relies on an ingress `configuration-snippet` to add `Secure`; workflow interpolates secrets inline into `run:` rather than `env:`; actions pinned to tags not SHAs; secrets passed as `--from-literal` argv. No hardcoded credentials found.
- **Recommendation:** Pin images by digest; add pod securityContext/NetworkPolicy; pass secrets via `env:`; pin actions.

### AW-2026-057 — Liquid metadata, request-id and credential hygiene — **Low** — New
- **Files:** `src/store/liquid.ts:112-113,203-210,285,322-326,426-432`, `src/scripts/liquid/sessions.ts:24-41,116-118`, `src/pages/Connect.vue:~527-541`.
- **Description:** Peer-chosen icon URL is fetched by the browser (IP leak/tracking); peer metadata persisted with only a shallow type check and no length caps; requests keyed by peer-chosen `id` rather than `(topic,id)` (cross-session confusion/DoS); `liquid:cred:*` entries survive disconnect with no removal UI. Stored data lands in the AES-encrypted wallet blob (not new exposure). No XSS found via `normalizeUrl`.
- **Recommendation:** `referrerpolicy="no-referrer"` or no remote icons; cap field lengths; key on `topic:id`; add credential cleanup.

### AW-2026-058 — `/payWC/:account/:payload` signs with the route account, not bound to `txn.sender` — **Low** — New
- **Files:** `src/pages/Sign.vue:~858-864,~1376-1384`, `src/scripts/wcNavigation.ts`, commit `fdce6c2`.
- **Description:** `payFrom` is the route param; `signTxClick` signs with its key/multisig params without asserting equality with the transaction sender. Pre-existing; commit `fdce6c2` does not let DApp data choose the key (fallback to txn sender only fills an empty URL segment and `ensureAccount` rejects foreign addresses). A mismatch yields an on-chain-invalid signature unless rekeyed.
- **Recommendation:** Force `payFrom = txn.sender` or error on mismatch.

### Informational
- **Folks lend USDC↔fUSDC conversion is well guarded:** goes through `assertFolksLendTxnsSafe` → `assertSwapTransactionsSafe`, whitelists axfer receivers (pool app/sender) and app calls (pool NoOp + single OpUp), builds locally from SDK constants. Residual: pool-call accounts/assets/boxes unchecked; `@folks-finance/algorand-sdk` trusted; no pre-sign simulation.
- **Slippage protection can be disabled** by the user (`biatec.ts`, `folks.ts`, `deflex.ts`), removing the only output bound under AW-2026-043.
- **Liquid does not auto-connect on refresh** (`liquid/init`/`reconnect` only from user actions in `Connect.vue`), consistent with the CLAUDE.md rule; WalletConnect also still initializes only from the Connect button.
- **Close/rekey warnings preserved** in `ConnectRequestsTable.vue`, `SignAll.vue`, and the shared `decodeSignRequests.ts`. Ledger refactor (`withLedger`, `ledgerPath`) has no signing-correctness regression.
