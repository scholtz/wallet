## 1. Executive summary

This audit covers `8001781..f8a74a0` plus a fresh static review of all nine in-scope areas: key material and encryption at rest, the five signing paths (sk, HD, Ledger, Falcon, multisig), the four dApp transports (WalletConnect v1/v2, Liquid Auth, Biatec Direct), chain-data trust, payment links and the merchant gateway, swaps and scheduled payments, supply chain, build and deployment, and web hygiene. All twenty remediations from the previous report are confirmed in source: **AW-2026-080, -083, -086, -088, -089, -095, -097 and -098 are Closed**, the other twelve remain Mitigated with the residuals already recorded.

The pass found **0 Critical, 0 High, 3 Medium, 8 Low and 1 Informational new findings**. No defect in key generation, derivation, encryption or the bytes that are signed was found; the Medium findings are all in the "what the user sees before clicking Sign" class:

- **AW-2026-100 (Medium):** the `/sign` review page never displays a `rekeyTo` taken from the transaction it is about to sign. Its rekey row is bound to the page's own form state, and the multisig row reads a field (`reKeyTo`) that algosdk v3 does not have, so the wallet's own rekey flow and any URL-delivered transaction are confirmed without the rekey target or warning being shown. Present since the algosdk v3 upgrade (PR #134, 2026-01-04) for the multisig row; the plain path predates it.
- **AW-2026-101 (Medium):** a dApp transaction that looks like an ARC-14 login (zero-amount self-payment with the `#ARC14` note) is relabelled "Authenticate", excluded from simulation and returned to the dApp automatically after one click, but the detector never checks `fee`, and no dApp transport caps fees. A self-payment with the account's spendable balance as its fee is fully broadcastable.
- **AW-2026-102 (Medium):** a payment link's `network=` parameter switches and persists the wallet's network without confirmation; an unknown value such as `custom` keeps the previous network's node and indexer while disabling every genesis cross-check.

The Low findings cover a bypassable HTML guard in front of the footer's `v-html` sink, a signed-transaction cache that outlives a rejected request, participation keys that are signed but never shown, a non-network-scoped in-memory asset cache, fee auto-raise driven by unchecked node parameters, wallet destruction behind a browser `confirm()` only, mnemonics copied to the clipboard without clearing, and the type-agnostic scheduler guard.

Verification at HEAD: unit 411/411, locale check clean, CI build/lint/type-check and the full Playwright E2E suite green on the PR head `3bf0348` (the merge adds only the CI deploy tag commit); locally, the Direct signing, WalletConnect multisig return, gateway and HD self-pay E2E specs were run against the production bundle (result in section 4). `pnpm audit --prod` is down from 12 to **11 advisories (2 high, 5 moderate, 4 low)**.

After this audit the risk registry holds 111 rows: **27 Open**, **33 Mitigated**, **43 Closed** and **8 Accepted**.

## 3. Findings

### AW-2026-100 — `/sign` review page never shows the `rekeyTo` of the transaction it signs — **Medium** — New

- **Affected:** `src/pages/Sign.vue:215-223` (rekey row `v-if="rekeyTo"`), `:802` (`rekeyTo = ref("")`, written only by the page's own pay form at `:1341`, `:1532`, `:1541`), `:354-363` (multisig row `v-if="multisigTxn?.reKeyTo?.publicKey"`), `:775-786` (`LooseTransaction` declares `reKeyTo?` so `vue-tsc` accepts it; algosdk v3 `Transaction` has `rekeyTo`), `:996-1004` (`isRekey` true only for `multisigDecoded.txn.rekeyTo` or route `type === "rekey"`), `:1986-2050` (unsigned decode path reads receiver/amount/asset/note/fee, never `rekeyTo`); `src/pages/Pay.vue:1062-1082` (own rekey flow builds `reKeyTo: state.rekeyTo` and pushes `/sign/<sender>/<b64>` with no type param); `src/router/index.ts:313-328` (`/sign` and `/payWC` render this component).
- **Description:** the review card shows type `pay`, pay-to, amount, fee and environment, but the rekey target comes only from the page's own form. For a transaction delivered as bytes (the wallet's own Rekey action, a `/sign/:account/:b64` deep link, the multisig `/payWC` return) no rekey row, red warning or "Rekey" title appears. The multisig row has been dead since PR #134 (2026-01-04) renamed the field. After submit, `:1486` does not run, so the local `rekeyedTo` bookkeeping only catches up on the next `wallet/syncAccountSigner`. Same defect class as Closed AW-2026-007 (`SignAll.vue` rekey column bound to a nonexistent field) and the CLAUDE.md `wc.ts` flat-shape bug.
- **Attacker precondition:** for the missing-confirmation case none (normal use). For deception, a transaction with a hostile `rekeyTo` must reach `/sign` or `/payWC` in an already-unlocked tab: a full page load locks the wallet and `Login.vue:255-265` redirects to the last account rather than the deep link, and dApp requests are first reviewed in `ConnectRequestsTable`/`SignAll.vue`, which do bind `txn.rekeyTo`. No in-app path that pushes an unreviewed dApp transaction to `/payWC` was found.
- **Impact:** the single most dangerous Algorand transaction field (account takeover) is absent from the page where the user clicks Sign on two in-app paths. Cryptographic signing is correct; this is a UI trust-cue failure (scope area 9).
- **Recommendation:** bind the rekey row and `isRekey` to `txn.value.rekeyTo` (plain path) and `multisigTxn.rekeyTo` (multisig path); drop `reKeyTo`/`from`/`to` from `LooseTransaction` so the type-checker catches the next rename; add an E2E that starts the wallet's own rekey flow and asserts the rekey warning on `/sign`.

### AW-2026-101 — ARC-14 "Authenticate" shortcut ignores the fee and auto-returns the signature; no dApp transport caps fees — **Medium** — New

- **Affected:** `src/scripts/encoding/arc14.ts:55-69` (`isArc14AuthTransaction`: type/group/rekey/close-to/amount/note/self-receiver, no `fee`, `lease` or validity-window check); `src/components/ConnectRequestsTable.vue:1338-1348` (`clickAccept` runs automatically when the request is ARC-14-only), `:1634-1647` (excluded from simulation; button relabelled "Authenticate with {realm}"), `:214-219` (ARC14 badge: "just a login, not a transfer"); admission handlers `src/store/wc.ts:421-469`, `src/shared/wc.ts:223-265`, `src/store/liquid.ts:490-547`, `src/store/direct.ts:385-466` (no fee ceiling); `src/scripts/liquid/guards.ts` (no `fee` reference); `src/store/arc14.ts:83` (the wallet's own auth transaction uses `fee = 0`).
- **Description:** a dApp sends a single zero-amount self-payment with an `X#ARC14` note and `fee = N`. The row shows the ARC-14 badge, the Sign button reads "Authenticate", the request is left out of the simulation, and on signing it is sent back without a second "Send back" step. The fee is shown in the "Total fee" column, but `Arc56RiskIcon` (`src/scripts/arc56/riskTxn.ts:31-45`) does not flag fees and the badge text tells the user it is not a transfer. The transaction is ungrouped and broadcastable by the dApp.
- **Attacker precondition:** any approved session (WC v1/v2, Liquid, Direct) for the account and one click on "Authenticate".
- **Impact:** irreversible loss of the fee amount, up to the spendable balance (griefing; the attacker gains nothing directly). More broadly, no dApp transaction on any transport is fee-bounded, whereas the wallet's own builders cap at 0.1 ALGO (`MAX_AUTO_FEE_MICROALGOS`) and swaps at 0.5 ALGO.
- **Recommendation:** require `fee === 0` (the wallet's own convention) in `isArc14AuthTransaction`, or at least `fee <= minFee`; add a dApp fee ceiling (e.g. refuse or require an explicit extra confirmation above 0.1 ALGO per transaction) in the shared admission guard; flag high fees in `isRiskyTransaction`.

### AW-2026-102 — Payment-link `network=` switches and persists the wallet network without confirmation; an unknown value disables the genesis checks while keeping the old hosts — **Medium** — New

- **Affected:** `src/pages/Pay.vue:1016-1018` (`setEnv({ env: parsed.network })` whenever it differs), `src/pages/Sign.vue:1314-1316` (same, not awaited); `src/store/config.ts:478-560` (`setEnv`: for a value with no preset and no genesis-list entry, `algod`/`indexer`/`participation` stay `""` and `setHosts` only overwrites truthy fields, so the previous network's hosts and tokens are kept while `env`/`envName` become the link's string), `:286-300` (persisted to localStorage); `src/store/algod.ts:155-159` and `src/scripts/dappRequestChecks.ts:46-50` (`env === "custom"` returns before any genesis comparison); `src/router/index.ts:310` and `src/pages/Settings.vue:535-537` (`/pay/:toAccount` is the `web+algorand:` protocol-handler target).
- **Description:** opening `algorand://ADDR?amount=1&network=custom` (link, QR, or protocol handler) in an unlocked wallet relabels the network as `custom`, persists it, and from then on `assertParamsMatchNetwork`, `checkTxGenesis` and `findGenesisMismatch` all return "ok" while the wallet still talks to the previous network's node. For a known value (`testnet-v1.0`) the link switches the real network silently.
- **Attacker precondition:** user opens an attacker-crafted payment link or QR while unlocked (payment links are the feature's normal input).
- **Impact:** persistent loss of the AW-2026-005/-063/-086 network-mismatch protections until the user notices and fixes Settings; account balances keyed by `env` appear empty; a subsequent dApp request for another network is no longer blocked. The env label is visible on the Pay form and navbar, which is why this is not High.
- **Recommendation:** only accept `network` values that resolve to a built-in preset or a genesis-list entry; ask for confirmation before switching; never persist a switch initiated by a link.

### AW-2026-103 — Footer renders the translated `footer.text` template into `v-html`; the locale HTML guard is bypassable — **Low** — New (residual of Closed AW-2026-036/-037)

- **Affected:** `src/components/Footer.vue:8-12` (`v-html="brandLineHtml"`), `:97-112` (interpolated values are escaped, the `$t("footer.text")` template itself is not; `{auditsLink}`/`{groupLink}`/`{discordLink}` expand to real `<a>` tags); `scripts/check-locales.ts:40` (`HTML_TAG_PATTERN = /<\/?[a-zA-Z][^>]*>/` requires a complete tag inside one value).
- **Description:** a locale value `"<img src=x onerror=... {auditsLink}"` has no `>` and passes the guard; after interpolation the injected `<a ...>`'s `>` closes the `img`. vue-i18n literal interpolation `{'<'}img ...{'>'}` also passes (the regex sees `<'`). `Changelog.vue:46-53` is the only other sink and escapes all source text first.
- **Attacker precondition:** a malicious translation merged into `src/locales/*.json` (the lightly reviewed contribution type that motivated AW-2026-037). Rendered only while a wallet is open, i.e. with decrypted key material in Vuex.
- **Impact:** stored XSS in the unlocked wallet context (key exfiltration) behind a repo-level precondition.
- **Recommendation:** render `footer.text` through `<i18n-t>` named slots as `FAQ.vue` does, removing the `v-html`; alternatively escape the translated template before substituting the link HTML, and tighten the guard to reject any `<` followed by a letter.

### AW-2026-104 — Signed-transaction cache is global across sessions and transports and survives a rejected request — **Low** — New

- **Affected:** `src/store/signer.ts:254-259` (`setSigned` keyed by `txID`), `:280-284` (`clearSignedCache`, called only from `config.ts:561` on network switch and `wallet.ts:1039,2076` on logout/destroy); `src/components/ConnectRequestsTable.vue:1442-1460` (`toBeSigned` consults the cache), `:1468-1469` (`needsSigning`), `:140-151` ("Send back" enabled once anything is signed).
- **Description:** a transaction signed in one request (then sent or rejected) re-appears as "Signed" with no Sign button in any later WC v1/v2 or Liquid request that carries the identical bytes, and "Send back" hands out the signature without re-review. Direct uses a fresh popup store and is unaffected.
- **Attacker precondition:** a dApp whose request the user signed-then-rejected (or an attacker holding the same bytes within the validity window) re-submits it.
- **Impact:** low; same bytes, same intent, bounded by `lastValid`. But an explicitly rejected request looks pre-approved.
- **Recommendation:** clear the cached signature when a request is rejected or answered; scope the cache by request id or session.

### AW-2026-105 — Key-registration participation keys are signed but never displayed — **Low** — New (residual of AW-2026-081)

- **Affected:** `src/scripts/txDetails.ts:36-41` (fields typed), `:141` (used only to classify online/offline), `:504-517` (summary returns kind and rounds); `src/components/ConnectRequestsTable.vue:250-259, 575-581` (rows show kind and vote rounds; grep for `voteKey`/`selectionKey`/`stateProofKey`/`voteKeyDilution` in the component: none).
- **Description:** an online `keyreg` is summarised as "Registers participation keys and takes the account online" with the valid rounds; the user cannot tell their own keys from attacker-supplied ones.
- **Attacker precondition:** approved WC/Liquid session for a staking account.
- **Impact:** the account goes online with keys the attacker controls (votes with the user's stake; no fund loss).
- **Recommendation:** show the three keys (base64, truncated) and the dilution in the keyreg detail rows; the participation page already knows the wallet's own keys and could mark a match.

### AW-2026-106 — In-memory asset metadata cache is not network-scoped — **Low** — New (sibling of AW-2026-090)

- **Affected:** `src/store/indexer.ts:140-144` (`setAsset` pushes without `env`), `:362-369` (`getAsset` returns the first `assets` entry with the same numeric id); consumers `Pay.vue:939-956`, `Sign.vue:1235-1247`, `SignAll.vue:405-418`.
- **Description:** the persistent cache is env-prefixed (and disabled on `custom`, AW-2026-090), but the Vuex array is consulted first by id only. After an in-session network switch (Settings, navbar, or AW-2026-102) an asset id present on both chains returns the previous chain's decimals, name and unit for amount entry and review.
- **Attacker precondition:** in-session network switch plus a colliding asset id (realistic for testnet/mainnet ids of similar magnitude, or forks).
- **Impact:** wrong base-unit scaling of the signed amount and a misleading asset name.
- **Recommendation:** key `setAsset`/`getAsset` by `env` as the persistent cache already is; clear the array in `setEnv`.

### AW-2026-107 — Fee auto-raise is driven by unchecked node parameters — **Low** — New

- **Affected:** `src/store/algod.ts:618-661` (`estimateRequiredFee` calls `getTransactionParams()` without `assertParamsMatchNetwork`; `groupUsage` from the node's simulate), `:351-371` (`signAndSend` raises `txn.fee` to the result after the click, success toast only), `src/pages/Sign.vue:1403-1432` (`checkAndAdjustFee` re-run at click time).
- **Description:** a node reporting `minFee = 100000` makes every self-built transaction carry 0.1 ALGO; the `MAX_NODE_MIN_FEE` guard that `getCheckedTransactionParams` applies is not applied on this fetch. Bounded by `MAX_AUTO_FEE_MICROALGOS`.
- **Attacker precondition:** malicious or compromised configured algod (AW-2026-010/-011).
- **Impact:** burn of up to 0.1 ALGO per transaction, after the user clicked on a lower displayed fee in `signAndSend` paths.
- **Recommendation:** route `estimateRequiredFee` through `getCheckedTransactionParams`; show the final fee before signing when it was raised.

### AW-2026-108 — Wallet destruction needs only a browser `confirm()` — **Low** — New

- **Affected:** `src/store/wallet.ts:2044-2062` (`destroyWallet`: `window.confirm`, then `db.wallets.delete`), reachable from `src/pages/Settings.vue:287-293`.
- **Description:** irreversible deletion of every key in the wallet from an unlocked session with no password re-entry, on the same screen as the backup download. `Export.vue:278-292` already re-checks the password for a far less destructive action.
- **Attacker precondition:** physical access to an unlocked device (inside the accepted AW-2026-030/-012 envelope).
- **Impact:** loss of keys, not theft.
- **Recommendation:** reuse `wallet/checkPassword` before destroying; require typing the wallet name.

### AW-2026-109 — Mnemonic and ARC-14 token copied to the system clipboard with no auto-clear — **Low** — New

- **Affected:** `src/pages/Account/Export.vue:14, 294-298, 471-472` (`copy-to-clipboard` of `state.mn`), `src/pages/Arc14.vue:83` (auth token).
- **Description:** no timed clear after copying; the clipboard is readable by any native app and by OS clipboard history/cloud sync.
- **Attacker precondition:** clipboard-reading software or OS clipboard sync on the user's device (within AW-2026-033, but this is an in-scope lever).
- **Impact:** mnemonic exposure beyond the export screen.
- **Recommendation:** clear the clipboard after ~60 s when it still holds the copied value; show a notice; consider removing the copy button for mnemonics in favour of the QR.

### AW-2026-110 — Scheduler response guard is type-agnostic; the deploy transaction is reviewed with a bare `appl` label — **Low** — New (residual of AW-2026-085)

- **Affected:** `src/scripts/scheduledPaymentTxns.ts:9-40` (refuses rekey, close-to and fee > 0.5 ALGO for own senders; any type passes), `src/pages/Account/ScheduledPayments.vue:325-345, 372-385`; `src/pages/Sign.vue:47-57` (for `appl` only `txn.type` is rendered: no app id, OnComplete, args or program hash), `:1030-1041` (appl/keyreg/acfg exempt from the address check).
- **Description:** a compromised `api-scheduler.biatec.io` response can return an `acfg` reconfiguring an ASA the user created, an `afrz`, a `keyreg`, or an `appl` with Update/Delete/ClearState on-complete; all pass the guard. The bootstrap group goes to `/signAll`, which flags these via `isRiskyTransaction`; the deploy transaction goes to `/sign`, which shows only the type.
- **Attacker precondition:** compromised scheduler API or MITM; user who created assets or apps.
- **Impact:** loss of control over user-created assets/apps with one click.
- **Recommendation:** replace the deny-list with a per-type allow-list (`pay`, `axfer`, `appl` create/NoOp with the expected app id); render app id, OnComplete and program hash on `/sign` for `appl` (the `DirectAppCard` already exists).
