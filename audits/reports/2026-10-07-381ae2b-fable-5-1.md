## 1. Executive summary

This audit covers the three commits since `fdce6c2`: the remediation pass for the 2026-10-04 audit (`fbecfe7`, AW-2026-049..058) and **Biatec Direct** (`b1540ea`), a third dApp transport in which the dApp opens the wallet in a popup and the two pages talk over `window.postMessage` with no relay. The Direct transport is well designed: the dApp identity is the browser-verified `event.origin`, every message must come from both the hinted origin and `window.opener`, one request per popup, grants are network-bound, only fully displayable transaction kinds are signed, and the ARC-60 login domain is finally bound to a browser-verified origin. The 25-test Playwright spec for it passed in this audit. No Critical finding was raised.

Nine new findings are recorded: **1 High, 4 Medium, 3 Low, 1 Informational**. The High finding (AW-2026-059) is a lost-update bug in multi-tab wallet persistence: a second unlocked tab that merely navigates re-saves its stale account list and can erase an account (with its private key) created in the other tab. Direct makes "two unlocked windows" a normal situation, and the new cross-tab merge protects only the Direct grants, not accounts. The Medium findings are: a password change silently reverted by another open tab (AW-2026-060); `/new-wallet` while unlocked cloning every key and the wrapped password into the new wallet (AW-2026-061); the still-shipped WalletConnect v1 path bypassing all the request-admission guards added in the last cycle and auto-approving sessions (AW-2026-062, which downgrades AW-2026-051 from Closed to Mitigated); and dApp transactions over WalletConnect/Liquid being network-checked only by the `genesisID` string, never by `genesisHash` (AW-2026-063; Direct does this correctly).

Of the ten prior findings, eight remediations were independently confirmed as described. AW-2026-058 is Closed but by a different mechanism than documented, and AW-2026-051 is reopened as Mitigated because of the v1 bypass. Dependency advisories rose from 8 to 9 (one new moderate via a test-runner dependency of `xhd-wallet-api`).

## 3. Findings

### AW-2026-059 — Stale tab's `saveWallet` overwrites accounts added in another tab (lost update of `privateAccounts`) — **High** — New
- **Files:** `src/store/wallet.ts:361-380` (`serializeWalletMergingSharedItems`), `:1649-1702` (`saveWallet`), `:862-865` (`lastActiveAccount` → `saveWallet`), `src/scripts/walletSharedItems.ts:13-27` (`SHARED_WC_KEYS = ["direct:sessions"]`), `src/pages/Sign.vue:2010-2013` (dispatches `wallet/lastActiveAccount` on mount of `/payWC`).
- **Description:** Commit `b1540ea` serialized wallet writes behind a Web Lock and merges *shared wc items* from the persisted record before writing. Everything else, including `privateAccounts`, is still serialized from the saving tab's in-memory snapshot. The lock orders writes; it does not detect that the snapshot is stale. `saveWallet` is dispatched automatically on mount of `Accounts.vue`, `AccountOverview.vue`, `Assets.vue`, `Transactions.vue`, `Sign.vue`, `Connect.vue` (via `wallet/updateAccount`) and on every account navigation (`wallet/lastActiveAccount`). Inside the Direct popup the multisig path detours through `/payWC`, whose `onMounted` calls `lastActiveAccount` and therefore saves the popup's snapshot.
- **Attacker precondition:** None (self-inflicted). The user has the same wallet unlocked in two browsing contexts (two tabs, or main tab + Direct popup), creates or imports an account in one, then navigates in the other.
- **Impact:** The new account record, including its `sk` / `hdMnemonic` / Falcon key, is removed from persistence. For a freshly generated key whose mnemonic was not written down, funds sent to it are unrecoverable. Also silently reverts deletions, renames, `backedUp` flags and rekey metadata.
- **Recommendation:** In `saveWallet`, re-read and decrypt the persisted record under the lock and merge `privateAccounts` by `addr` (never drop an address present in the persisted record unless this tab explicitly deleted it), or move account mutations to the `wcUpdateItemFresh`-style read-modify-write. Add a `BroadcastChannel`/`storage` signal so other tabs re-hydrate. Add a two-page Playwright regression (create account in page A, navigate in page B, reopen wallet, assert both accounts present).

### AW-2026-060 — Password change silently reverted by any other unlocked tab (old password keeps working) — **Medium** — New
- **Files:** `src/store/wallet.ts:1589-1648` (`changePassword`), `:361-380` (decrypt failure caught and swallowed at `:372-375`), `:1691-1698` (`encryptWalletData(data, oldPass, walletRecord.data)` then `db.wallets.update`), `src/scripts/encoding/walletCrypto.ts:142-179` (`reuseSaltFrom` only reuses salt; it never verifies the password against the existing record).
- **Description:** After tab A changes the password, tab B still holds `state.pass` wrapping the old password. On tab B's next automatic `saveWallet`, decrypting the persisted record with the old password fails, the error is swallowed ("fall back to this tab's copy rather than failing the save"), and the whole wallet is re-encrypted with the **old** password and written back. Tab A showed a success toast; the new password fails at the next login and the old one works. WalletConnect v1 session rows in the `wc` Dexie table are also never re-encrypted on password change.
- **Attacker precondition:** Someone who learned the old password (shoulder-surfing, shared device) retains access after the user believes they rotated it. Requires a second tab open during the change, which is common.
- **Impact:** Password rotation is not effective; combined with AW-2026-059 the stale tab also reverts account changes.
- **Recommendation:** Treat decryption failure in `serializeWalletMergingSharedItems` as fatal for the save (do not write; lock the tab and ask to re-login). Broadcast password changes to other tabs. Re-encrypt `wc` table rows in `changePassword`.

### AW-2026-061 — `/new-wallet` while a wallet is unlocked clones all keys and the wrapped password into the new wallet — **Medium** — New
- **Files:** `src/store/wallet.ts:1760-1795` (`createWallet` serializes `this.state.wallet` as-is), `:805-818` (`pass` = `CryptoJS.AES.encrypt(pass, rs1)` with `rs1` in `localStorage`), `src/router/index.ts` (no navigation guard on `/new-wallet`), `src/components/NewWallet.vue:146-162`, `src/components/Login.vue:190`, `src/components/Navbar2.vue:349`.
- **Description:** `createWallet` does not start from a fresh `state()`. If a wallet is already open, the new wallet record contains the open wallet's `privateAccounts` (with secrets), its `wc` key store and its `pass` field. The navbar hides the link while unlocked, but the route has no guard and is reachable by URL or same-origin link.
- **Attacker precondition:** The user creates a second wallet (for example a "demo" wallet with a weak password for someone else on the same device) without logging out first, or is lured to the same-origin `/new-wallet` URL.
- **Impact:** Anyone who can open wallet B obtains every key of wallet A, and, because B's blob carries A's `rs1`-wrapped password and `rs1` is in the same browser's `localStorage`, A's password as well.
- **Recommendation:** `createWallet` must `logout` first and serialize a fresh state. Serialize an explicit allow-list of fields (`privateAccounts`, `lastPayTo`, `lastActiveAccount`, `wc`) instead of the whole `WalletState`, so `pass`/`isOpen`/`time` never enter a ciphertext blob (also see AW-2026-066).

### AW-2026-062 — WalletConnect v1 path bypasses all request-admission guards and auto-approves sessions — **Medium** — New (downgrades AW-2026-051 to Mitigated)
- **Files:** `src/shared/wc.ts:222-246` (`handleSessionRequest` calls `connector.approveSession({accounts:[address], chainId: 4160})` with no user prompt), `:258-300` (`handleCallRequest` decodes and commits `wc/addRequest` with no `admitEnvelope`/`admitTransactions`/`findUnauthorizedSenders`), `:136-195` (`decodeTransactions` still reads the flat `decoded.assetIndex`/`amount`/`from`, which are undefined on algosdk v3), reachability `src/pages/Connect.vue:48-72, 859-861`, `src/store/wc.ts:589, 610-615`, `src/store/wcClient.ts:245-252`, `package.json:46`.
- **Description:** The 2026-10-04 remediation applied the shared admission module to WalletConnect v2, Liquid and (in `b1540ea`) Direct, but the opt-in v1 client was left untouched. On that path there is no sender-vs-approved-account check, no transaction/pending caps, pre-signed blobs are registered in `signer.signed` during decode, and the request-summary fields are blank for the same reason CLAUDE.md records as fixed for v2.
- **Attacker precondition:** User clicks "Enable WalletConnect v1" and pairs with a malicious v1 dApp (the session is approved without any prompt).
- **Impact:** Decoy/confusion requests for any wallet account (user must still click Sign), blank summary columns, request flooding. No silent signing.
- **Recommendation:** Remove the v1 client (AW-2026-024), or route `handleCallRequest` through `decodeSignTxnTransactions` + `admitEnvelope`/`admitTransactions` with `approved: [address]` and require explicit session approval.

### AW-2026-063 — dApp transactions over WalletConnect/Liquid are network-checked only by the `genesisID` string, not `genesisHash`, and a mismatch does not block signing — **Medium** — New
- **Files:** `src/components/ConnectRequestsTable.vue:1045-1051` (`genesisMismatch`: `Boolean(genesisId && env && genesisId !== env)`), `src/pages/Sign.vue:846-857` (`fatal`, genesis-id only), `src/store/signer.ts:116-122` (`resolveTxEnv` trusts the dApp's `genesisID` to pick the rekey record), `src/shared/decodeSignRequests.ts` (no hash comparison). Contrast: `src/scripts/direct/protocol.ts:389-400` (`txnGenesisMatches`) and `src/store/direct.ts:401-412`.
- **Description:** `gen` is optional in the Algorand encoding. A transaction with `gen` omitted and a mainnet `gh` while the wallet is on testnet produces no warning (the check short-circuits on a falsy `genesisID`), yet the signature is valid on mainnet. With `gen` present but mismatched the UI shows an error `Message` but the Sign button is still enabled. The Direct transport already compares the 32-byte hash per transaction and refuses with 4004; the older transports do not.
- **Attacker precondition:** Malicious WC/Liquid dApp; victim has the same key funded on another network than the one selected (common for testnet testing).
- **Impact:** User signs a transaction for a network other than the one shown as active.
- **Recommendation:** Reuse `txnGenesisMatches`/`expectedGenesisReference` from `scripts/direct/protocol.ts` in the shared decoder, refuse (4004) when the hash does not match the active network, treat a missing `gen` as "check hash", and hard-block Sign on mismatch.

### AW-2026-064 — Group completeness is never verified for dApp sign requests (all three transports) — **Low** — New
- **Files:** `src/shared/decodeSignRequests.ts:98-174`, `src/store/wc.ts`, `src/store/liquid.ts`, `src/store/direct.ts:333-441` (no `computeGroupID` anywhere on the dApp path; grep of `src/shared` and the three stores is empty).
- **Description:** ARC-1 requires every member of a group to be present. The wallet accepts a request containing a subset of group G, or members whose `grp` does not match the recomputed group id. Hidden members can be app calls that consume the user's signed transaction in ways not shown. Simulation then reports a failure, but signing is not blocked.
- **Recommendation:** In admission, bucket by `group`, recompute `algosdk.computeGroupID` over each bucket and refuse (4201 `invalidGroupId` exists already) on mismatch or incomplete set.

### AW-2026-065 — `signer.signed` is pre-populated with dApp-supplied "pre-signed" blobs and never cleared on logout — **Low** — New
- **Files:** `src/store/signer.ts:217-222` (`setSigned` keys by `tx.txn.txID()` with no signature verification), `:243` (`clearSignedCache`, only called on network switch from `config.ts:561`), `src/store/wallet.ts:899-937` (`logout` resets `wc`/`liquid`/`direct` but not the signer map), `src/store/wc.ts:462-463`, `src/store/direct.ts:426-428`, `src/store/liquid.ts` (`signer/setSigned` for every `{txn,sig}` envelope the dApp sends).
- **Description:** For a pre-signed entry whose sender is the user's own approved account, the UI shows "Signed" for a transaction the user never signed, `clickSign` refuses to sign it (`txId in signed` early return), and "Send back" echoes the dApp's own blob. Cannot forge a valid signature, so no fund loss. The map is unbounded and survives logout, so blobs leak into the next wallet opened in the same tab.
- **Recommendation:** Keep dApp-supplied blobs in a per-request map; only exempt them when the sender is not an own account; reset the signer module on logout.

### AW-2026-066 — Empty/weak passwords accepted on create and change; serialized blob includes the wrapped password and session fields — **Low** — New
- **Files:** `src/store/wallet.ts:1597` (`changePassword` only checks `passw2 != passw3`), `:1764` (`createWallet` checks only `name`), `:376-379, 1777-1780` (whole `WalletState` incl. `pass`, `isOpen`, `time` serialized), `src/components/NewWallet.vue:30-40`, `src/pages/Settings.vue:216-237` (no `required`/length validation).
- **Description:** An empty new password re-encrypts the wallet under PBKDF2("") — effectively plaintext for anyone holding the IndexedDB blob. Separately, every encrypted blob carries the CryptoJS-wrapped wallet password (circular for the same wallet, but any plaintext leak of a blob also leaks the password; see AW-2026-061 and AW-2026-026).
- **Recommendation:** Enforce a minimum password length in the actions (not only the UI). Serialize an explicit field allow-list.

### AW-2026-067 — Biatec Direct residual observations — **Informational** — New
- **Files:** `src/scripts/direct/protocol.ts:353-386` (`checkRequestNetwork` returns ok for any hash when `env === "custom"`), `src/scripts/encoding/arc60Domain.ts:10-25` (hostname or host accepted), `src/shared/direct.ts`, `docker/default.conf:8-12`, `index.html` (no CSP meta), `.github/workflows/gh-pages.yml` (no header control).
- **Observations:** (a) With a custom node the dApp chooses the network; the popup shows a warning with the hash prefix, as documented. (b) ARC-60 AUTH over Direct accepts the hostname for any port of that host, matching WebAuthn RP-ID semantics; two ports of one host collapse to one login identity (`http://localhost:5173` and `http://localhost:6666` both authenticate as `localhost`; loopback is flagged as development). (c) The opener can navigate the popup to any wallet route; a navigation reloads and locks the wallet, so this is a same-origin phishing surface no worse than any deep link, and the single-use channel prevents a second `ready`. (d) `frame-ancestors`/`X-Frame-Options` exist only in the nginx deployment; on GitHub Pages/Vercel the popup's anti-framing rests solely on the `window.top !== window.self` check (folded into AW-2026-015). (e) `lastUsedAt` of a grant is never updated on use. No action required beyond the linked rows.
