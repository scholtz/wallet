## 1. Executive summary

This audit covers `a5217ae..8001781` (11 commits: the AW-2026-076..079 remediation branch and its CI deploy) plus a fresh static review of all nine in-scope areas, with the whole `src/store`, `src/shared`, `src/scripts` tree and the signing/dApp/payment pages read in full. The four remediations from the previous audit are confirmed and **AW-2026-076, -077, -078 and -079 are Closed**.

The deep pass found **two High, four Medium, eleven Low and three Informational new findings (0 Critical)**. Both High findings are long-standing and were missed by the thirteen previous audits:

- **AW-2026-080 (High, Critical impact):** creating an HD (ARC-52) account in "create" mode displays one 24-word phrase, asks the user to confirm they backed it up, and then stores a *different*, freshly generated phrase. The written-down backup cannot recover the account, and the confirmation sets `backedUp: true`, which silences the wallet's own "not backed up" warning. Present since the HD feature landed (`332ace9`, 2026-07-01). Recovery is still possible from the Export page while the wallet database exists, so this is a backup-integrity failure rather than an immediate theft path.
- **AW-2026-081 (High):** over WalletConnect (v1 and v2) and Liquid Auth, asset-config, asset-freeze and key-registration transactions are accepted and can be signed (including through "Sign all") while none of their type-specific fields (new manager/reserve/freeze/clawback, asset destroy, freeze target, `nonParticipation`) is displayed. Only Biatec Direct refuses these kinds.

The Medium findings concern an under-displayed contract update/create path on WC/Liquid, a unit mismatch in the `fee=` payment-link parameter that lets a link pre-fill a flat fee a thousand times larger than intended, the merchant gateway's "payment received" signal that checks nothing but address and note prefix, and scheduled-payment transactions from an external API reaching the signing pages without structural validation.

## 3. Findings

### AW-2026-080 — HD account "create" mode shows and confirms a mnemonic that is not the one stored — **High** (Critical impact when a backup is relied on) — New
- **Affected files:** `src/pages/NewAccount/HdWallet.vue:87-96` (`setMode`), `:110-120` (`createAccount`), `:127-131` (`onMounted`), `:168-250` (template), `src/store/wallet.ts:1256-1301` (`addHdWalletAccount`).
- **Description:** `onMounted` and `setMode("create")` generate `state.mnemonic = generateHdMnemonic()` and the template renders those words as the "master mnemonic" with flip cards, a copy button, a QR code and the "I have safely backed up my mnemonic" toggle. `createAccount` then dispatches `wallet/addHdWalletAccount` with `mnemonic: state.mode === "import" ? state.mnemonic : undefined` and `backedUp: state.confirmedBackup`. In the store, `const finalMnemonic = mnemonic?.trim() || generateHdMnemonic();` generates a *second* phrase, derives the address from it and persists it as `hdMnemonic`. The phrase the user wrote down never reaches the store.
- **Attacker precondition:** none; ordinary "New account → HD wallet → Create" flow.
- **Impact:** the user's paper/QR/clipboard backup does not restore the account (a different account is derived); `backedUp: true` suppresses the wallet's not-backed-up warning, so the user is never prompted to export the real phrase. If the device or the IndexedDB record is lost, funds on the HD account (and all derived child accounts, which share this root) are unrecoverable. While the record exists, the Export page reveals the actual phrase. `NewWallet.vue:171` (first-wallet creation) intentionally passes no mnemonic and leaves `backedUp` false, so that path is correct.
- **Existing tests:** `playwright/e2e/create-hd-wallet-account.spec.ts` and `hd-account-auto-backup.spec.ts` assert only the warning text, never that the exported phrase equals the displayed one.
- **Recommendation:** pass `state.mnemonic` in create mode (and make `addHdWalletAccount` require a mnemonic rather than silently generating one), then add an E2E that creates an HD account, exports it, and asserts equality with the words shown at creation. Consider a backup quiz (as `Ed25519.vue` has) before allowing `confirmedBackup`.

### AW-2026-081 — WalletConnect and Liquid sign `acfg`, `afrz` and `keyreg` transactions with their type-specific fields undisplayed — **High** — New
- **Affected files:** `src/store/wc.ts:405-487`, `src/store/liquid.ts:452-532`, `src/shared/wc.ts:191-299` (no transaction-type filter), `src/components/ConnectRequestsTable.vue:320-669` (per-transaction expansion), `:1092-1113` (`clickSignAll`); compare `src/scripts/direct/protocol.ts:276-347` (Direct refuses everything but `pay`/`axfer`/`appl`).
- **Description:** the shared admission (`admitTransactions`) checks sender scope, caps, group id and genesis, but not the transaction type. The expansion table has rows for sender, receiver, fee, asset/amount, rekey-to, close-to, clawback sender, validity, type, note, group, on-complete, app id, app args, accounts, foreign assets, boxes and genesis. A grep for `assetConfig|assetFreeze|keyreg|nonParticipation|voteKey|freezeAccount|manager|reserve` across `ConnectRequestsTable.vue`, `Arc56CallDetails.vue`, `Arc56RequestSummary.vue` and `TransactionGroupSimulation.vue` returns nothing except the clawback-sender row. An `acfg` therefore renders as a row reading `acfg`, sender and fee.
- **Attacker precondition:** any approved WalletConnect or Liquid session for an account that manages an ASA (for `acfg`/`afrz`) or any account at all (for `keyreg`).
- **Impact:** a dApp can obtain, with one click on "Sign all", a signature that hands the asset's manager/reserve/freeze/**clawback** authority to the attacker (clawback can then seize every holder's balance), destroys the asset, freezes arbitrary holders, or registers `nonParticipation=true` (irreversible on-chain). The simulation panel reports balance changes only, so none of these effects appears there either.
- **Recommendation:** either refuse these kinds on WC/Liquid as Direct does, or add explicit rows with red warnings for every `assetConfig`, `assetFreeze` and `keyreg` field (and refuse `stpf`/`hb`). Add E2E negative cases per kind.

### AW-2026-082 — Application create/update over WC/Liquid shows no program fingerprint; `lease`, `foreignApps`, schemas and `extraPages` are displayed on no transport — **Medium** — New
- **Affected files:** `src/components/ConnectRequestsTable.vue:485-524` (UpdateApplication badge), `:854` (`showAppCard = compact && isLifecycle(...)`), `src/components/DirectAppCard.vue`.
- **Description:** the program size/SHA-256/address card from AW-2026-071 renders only inside the Direct popup (`compact`). On WC/Liquid an `UpdateApplication` shows a warning badge and the app id, with no `approvalProgram`/`clearProgram` fingerprint and no comparison with the deployed program. `lease`, `foreignApps`, global/local schema and `extraPages` have no row anywhere, although `lease` and `foreignApps` change signed bytes and semantics.
- **Attacker precondition:** WC/Liquid session approved for an application creator account.
- **Impact:** a dApp can have a creator replace contract code with no way to review what is deployed; `lease` is signed invisibly (low standalone impact).
- **Recommendation:** render `DirectAppCard` (or equivalent) for lifecycle calls on every transport; add `lease`/`foreignApps`/schema rows.

### AW-2026-083 — `fee=` payment-link parameter is read as whole ALGO by the payment pages but emitted as microalgos by the wallet's own gateway; URI-supplied flat fees are not capped — **Medium** — New
- **Affected files:** `src/shared/algorand-protocol-parse.ts:116-125`, `src/pages/Pay.vue:1005-1007`, `:1407-1411`, `:626` (`feeLong = state.fee * 1e6`), `src/pages/Sign.vue:1294-1296`, `:956`, `:1396-1408` (`feeExceedsMax`), `src/store/algod.ts:280-283`, `src/pages/PaymentGateway.vue:451`, `src/pages/Merchant.vue:394-395`, `public/manifest.json:5-9` (`web+algorand` → `/pay/%s`).
- **Description:** without a `decimals` parameter the parser passes `fee` through as a raw string. `Pay.vue` does `state.fee = Number(parsed.fee)` and scales by 10^6, so `fee=1000` becomes a 1000 ALGO flat fee. The gateway builder writes `"&fee=" + Math.round(this.fee * 1000000)` (microalgos) and the merchant page divides by 10^6 to display "x ALGO", so the wallet's own `/gateway` → "Pay with web wallet" → `/pay/...` chain produces this mismatch. `algod/makePayment` sets `params.fee = BigInt(payload.fee); flatFee = true` and `feeExceedsMax` on the review page is driven only by the *simulated required* fee (`estimate.requiredFee > MAX_AUTO_FEE_MICROALGOS`), never by the declared fee; the fee row is shown but nothing blocks or highlights an absurd value. The `InputNumber :max="1"` on `Pay.vue:288` is not applied to a programmatically set model.
- **Attacker precondition:** user opens an `algorand://ADDR?amount=…&fee=N` link or scans such a QR (merchant gateway, phishing page, printed code), clicks Review and Sign without reading the fee row.
- **Impact:** the whole declared fee is burned on confirmation.
- **Recommendation:** parse `fee` as microalgos consistently; refuse or clamp URI-supplied `feeLong > MAX_AUTO_FEE_MICROALGOS` with a blocking error on the review page; add unit tests for the parser round-trip with `PaymentGateway`.

### AW-2026-084 — Merchant gateway reports "payment received" and auto-POSTs to the merchant when *any* transaction touching the payee carries the note prefix — **Medium** — New
- **Affected files:** `src/pages/Merchant.vue:185-191` (`isPaid`), `:373-383` (`searchForTransactions`: `.address(addr)` + `.notePrefix(note)` only), `:340-356` (countdown → `this.$refs.sendToMerchant.submit()`), `:73-86` (form posts only `txId`).
- **Description:** `isPaid` is `transactions.transactions.length > 0`. The indexer query does not constrain `addressRole("receiver")`, `currencyGreaterThan`, `assetID`, `minRound`/`afterTime`. The indexer helpers that do bound amount (`src/store/indexer.ts:239-322`) are not used here.
- **Attacker precondition:** a payer who controls what they send; or a merchant reusing an `xnote`; or any earlier transaction with the same note prefix (the default `a-wallet/<uuid>` is random, merchant-supplied notes often are not).
- **Impact:** a 0-amount payment, a payment in the wrong asset, a transaction *sent by* the payee, or an old transaction makes the page show "Payment received" and after 10 s POST a `txId` to the merchant's success URL. A merchant that trusts the gateway's UI (the page's copy implies the gateway verified payment) is defrauded; a diligent merchant must verify the `txId` on-chain.
- **Recommendation:** constrain the query to receiver role, exact asset id, amount ≥ expected, and a round/time floor captured at page load; state in the UI and docs that the merchant must verify `txId`.

### AW-2026-085 — Scheduled-payment transactions from `api-scheduler.biatec.io` enter `/sign` and `/signAll` without structural validation — **Medium** — New
- **Affected files:** `src/pages/Account/ScheduledPayments.vue:304-342` (`tx-create` → `signer/toSign` → `/sign/...`), `:353-374` (`bootstrap` → `signer/toSignArray` → `/signAll`), `src/pages/Account/ScheduledPaymentDetail.vue:1173-1181`, `src/pages/SignAll.vue:257-261`, `:309-315`.
- **Description:** unlike the swap path (`assertSwapTransactionsSafe` before every aggregator signature), transactions decoded from the scheduler API response are placed straight into the signer state and signed for any wallet-owned sender on confirmation. `SignAll` highlights rekey/close and now blocks genesis mismatch (AW-2026-077), but there is no allow-list of application ids, no fee bound (fees are fixed by the API), and in the single-transaction path only `txs[0]` is signed while other returned transactions are silently dropped. `state` (including `hash`/`client`) round-trips through `localStorage("currentAction")` and is interpolated unencoded into the API URL path (same-origin only).
- **Attacker precondition:** compromised or MITM'd scheduler API (TLS protects the transport; the service is operated by the wallet's author).
- **Impact:** arbitrary transactions presented for signature with one-click "Sign all"; rekey/close are flagged, application calls are not constrained.
- **Recommendation:** run `assertSwapTransactionsSafe` plus an application-id allow-list (`getPoolManagerApp(env)`) before `toSign`/`toSignArray`; reject responses that return more transactions than will be signed.

### AW-2026-086 — Genesis-hash cross-check of the configured node is inactive until the remote genesis list has been fetched (startup restore path) — **Low–Medium** — New (residual of AW-2026-005/011)
- **Affected files:** `src/store/algod.ts:155-181` (`assertParamsMatchNetwork`), `src/store/config.ts:226-233` (env/host restored from localStorage without `setEnv`), `src/store/publicData.ts` (`getGenesisList` callers: `config.ts:492`, `Settings.vue:456`, WC chain-id paths only).
- **Description:** the hash check runs only when `rootState.publicData.genesisList` has an entry for the env; nothing on app start or wallet open dispatches `publicData/getGenesisList`, so a session that restores `env`/`algodHost` from localStorage and goes straight to Pay checks only `params.genesisID !== env`, a string the node itself supplies. The hardcoded `KNOWN_NETWORKS` hash table used by the dApp paths is not consulted. The remote list and the remote host list also come from the same origin, so even when loaded the check is not independent.
- **Impact:** a malicious or misconfigured custom-host node for a named network can supply foreign-network params for wallet-originated payments in the common startup state. Requires AW-2026-010.
- **Recommendation:** check `KNOWN_NETWORKS` first (fail closed for built-in envs) and fall back to the CAIP10 list only for others.

### AW-2026-087 — ARC-14 realm is dictated by the remote service and tokens are cached by realm only — **Low** — New — *Needs verification*
- **Affected files:** `src/store/participation.ts:117-124`, `:145-151`, `src/store/fa2.ts:66-94`, `src/store/arc14.ts:63-68`, `:121-126`, `src/pages/Pay.vue:1433-1445`, `src/pages/Sign.vue:1875-1888`.
- **Description:** the participation and 2FA hosts return the realm string the wallet signs; tokens are stored as `address2chain2realm2token[chain][addr][realm]` and later looked up by realm string and sent to whichever service claims it (hardcoded realms `BiatecRouter#ARC14`, `BiatecScan#ARC14` elsewhere). A malicious provider (hosts come from the remote list, AW-2026-011) could return another service's realm and receive a token valid there for the ~1000-round window (AW-2026-021). Whether the relying services accept such a token could not be verified from this repo.
- **Recommendation:** key the cache by host and realm, and refuse realms that do not match the host's expected pattern.

### AW-2026-088 — Secret-key signing resolves the rekey chain against the UI network, not the transaction's network; the actual signing key for rekeyed accounts is never shown — **Low** — New
- **Affected files:** `src/store/signer.ts:294-301` (`resolveEnvRekey(..., env)` with tx/verified env), `:345-349` (`signBySk({ from: payload.from })`), `:593-607`, `src/store/wallet.ts:971-999` (`getSK` uses `this.state.config.env`), `:155-166`.
- **Description:** `signTransaction` picks the signer for the transaction's network, but the sk branch then re-resolves via `getSK`, which follows `account.data[config.env].rekeyedTo`. Reachable through Direct (which signs for foreign networks by design) and pasted transactions: with the wallet on mainnet and A→B rekeyed on mainnet only, a testnet transaction from A is signed with B's key (invalid on chain); the reverse yields A's key where B's was needed. The review UI shows only `sender`, never "signed by B".
- **Impact:** wrong-key signatures (rejected on chain) and an undisclosed signing key; no path to an unapproved account was found (admission is on `txn.sender`, the rekey map is wallet-local).
- **Recommendation:** pass `signerAccount.addr` to `signBySk`/`getSK` or give `getSK` an `env` parameter; show the resolved signer in the request table.

### AW-2026-090 — Asset decimals/name/unit come only from the configured indexer, are cached in localStorage without TTL, and the cache key is shared by every "custom" network — **Low** — New
