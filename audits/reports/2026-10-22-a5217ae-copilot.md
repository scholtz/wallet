## 3. Findings

### AW-2026-076 — Unvalidated URL-supplied `:href` (`origcode`, `settings.cancel`), auto-submitted `<form :action="settings.success">`, and `setHosts` mutation on public `/gateway` page — **Medium** — New
- **Status:** New
- **Affected files:** `src/pages/Merchant.vue:49-85`, `src/pages/Merchant.vue:170-198`, `src/pages/Merchant.vue:208-235`, `src/pages/Merchant.vue:289-331`, `src/shared/algorand-protocol-parse.ts:17-31`.
- **Description:** The unauthenticated route `/gateway/:b64/:settings?` (`Merchant.vue`) decodes `:b64` into `this.origcode` and `:settings` into `this.settings` (via `atob` / `base64url.decode` + `JSON.parse`). Three unsafe sinks consume these attacker-controlled values:
  1. `<a :href="origcode">` (`Merchant.vue:50,55`) and `<a v-if="settings.cancel" :href="settings.cancel">` (`Merchant.vue:65`) bind raw strings without scheme validation. In `parseAlgorandProtocolParameters` (`src/shared/algorand-protocol-parse.ts:26-29`), any input not starting with `algorand://` or `web+algorand://` simply sets `payload.payTo = result` without error, so `b64decode.error` is never set when `origcode` is `javascript:...`. If a user clicks "Pay with QR", "Pay with native wallet", or "Cancel payment" on a crafted `/gateway/...` link, a `javascript:` URI executes in the wallet's origin.
  2. `<form v-if="isPaid && settings.success" ref="sendToMerchant" :action="settings.success" method="POST">` (`Merchant.vue:73-86`) is automatically submitted after a 10-second countdown (`this.$refs.sendToMerchant.submit()` at `Merchant.vue:215`) once `searchForTransactions` returns any transaction matching `addr: b64decode.payTo` and `note: b64decode.paynote`. An attacker can point `payTo`/`paynote` at an already-confirmed historical transaction so `isPaid` becomes `true` immediately on first poll (5 s), triggering an automatic POST redirect (or `javascript:` form action execution) without a click.
  3. `mounted()` unconditionally calls `this.setNetwork()` (`Merchant.vue:187,289-331`), which dispatches `config/setHosts` (`localStorage.setItem("algodHost", ...)`) based on `b64decode.network`, overwriting the user's persisted Algod/Indexer host settings (and for `aramidmain` setting `algod: "https://algod.aramidmain.a-wallet.net"`, an older endpoint different from `NETWORK_PRESETS`).
- **Attacker precondition:** Victim opens a crafted `/gateway/<b64>/<settings>` URL on the wallet origin (and either clicks one of the payment/cancel buttons, or waits ~15 seconds for the auto-submit timer when `payTo`/`paynote` matches an existing on-chain transaction).
- **Impact:** DOM XSS in the wallet origin (`javascript:` URI in `href` or `form.action`), giving access to `localStorage` (`rs1`, persisted host config) and IndexedDB (`AWallet` encrypted blobs), or open redirect to a phishing page after payment; plus silent overwriting of the user's configured node/indexer endpoints in `localStorage`.
- **Recommendation:**
  1. Require `origcode` to start with `algorand://` or `web+algorand://` (reject and render an error state otherwise).
  2. Validate `settings.cancel` and `settings.success` via `new URL(...)` and allow only `https:` (and `http:` on loopback), rejecting `javascript:`, `data:`, and relative protocol-less schemes.
  3. Do not mutate global `config/setHosts` (`localStorage`) from the public `/gateway` page; use a local `algosdk.Indexer` client for the payment poll or only switch via `config/setEnv` with user consent.

### AW-2026-077 — `SignAll.vue` omits network genesis verification and Falcon-1024 fee estimation; `ScheduledPaymentDetail.vue` passes a typo key to `signer/toSign` — **Medium** — New
- **Status:** New
- **Affected files:** `src/pages/SignAll.vue:158-199`, `src/pages/SignAll.vue:275-315`, `src/pages/Account/ScheduledPayments.vue:315-370`, `src/pages/Account/ScheduledPaymentDetail.vue:495-506`.
- **Description:**
  1. Unlike `ConnectRequestsTable.vue` (which enforces `checkTxGenesis` / `findGenesisMismatch` per AW-2026-063) and `Sign.vue` (which checks `txn.genesisID !== envName` in `fatal` and runs `checkAndAdjustFee` via `algod/estimateRequiredFee`), `SignAll.vue` displays `genesisID` and `genesisHash` only inside the collapsed row expansion (`SignAll.vue:726-733`) and performs no check before `clickSign` or `clickSignAll` dispatches `signer/signTransaction`. Transactions loaded into `signer.toSignArray` (for example from `https://api-scheduler.biatec.io/v1/tx/...` in `ScheduledPayments.vue:338-360`) are signed even if their genesis hash/ID targets a different network than the one selected in the wallet.
  2. `SignAll.vue` does not estimate or warn on insufficient fees for Falcon-1024 post-quantum accounts (`isFalcon1024Signer` / `lowFalconFee`), so Falcon-signed transactions with a 0.001 ALGO fee will sign and fail at broadcast.
  3. In `src/pages/Account/ScheduledPaymentDetail.vue:498`, `withdrawFromEscrow` dispatches `await store.dispatch("signer/toSign", { txx: grouped[0] })` (`txx` instead of `tx`), so `store.state.signer.toSign` is set to `undefined` (fortunately `/sign/:account/:rawSignedTxnInput` reads the transaction from the route parameter, but the store state is corrupted).
- **Attacker precondition:** A compromised or misconfigured external transaction builder (`api-scheduler.biatec.io` or a future caller of `signer/toSignArray`) returning transactions for a different network than the user's selected network, or a user switching networks while on `/signAll`.
- **Impact:** Cross-network signing without a blocking check or top-level warning on `/signAll`; UX/broadcast failure for Falcon-1024 accounts on `/signAll`.
- **Recommendation:** Run `findGenesisMismatch(state.transactions.map(t => t.txn), store.state.config.env)` in `SignAll.vue` (disabling Sign/Sign All and showing an error `Message` on mismatch, plus clearing `signer.signed` / `state.transactions` signatures on network switch), surface `lowFalconFee` warnings, and fix `{ txx: grouped[0] }` → `{ tx: grouped[0] }` in `ScheduledPaymentDetail.vue:498`.

### AW-2026-078 — `wallet/importWallet` accepts arbitrary strings into IndexedDB without validating ciphertext format or JSON structure — **Low** — New
- **Status:** New
- **Affected files:** `src/store/wallet.ts:2079-2106`, `src/pages/Wallet/ImportWallet.vue:99-116`, `src/pages/Settings.vue:304-312`.
- **Description:** `Settings.vue` exports a wallet backup as `btoa(walletRecord.data)` in a `.dat` file, while `ImportWallet.vue` reads the uploaded file as raw UTF-8 text (`reader.readAsText(uploadedFile)`) and passes `data: file.value` directly to `wallet/importWallet`. `importWallet` only checks `if (!name)` and `if (!data)` before writing `await db.wallets.add({ name, data })` and calling `markWalletUsed(name)`. It does not:
  - Decode base64 if the user uploads the `.dat` file exported by `Settings.vue` (`Settings.vue:466` calls `btoa(walletRecord.data)`, whereas `openWallet` expects `walletRecord.data` to start with `AWEv1.` or be a CryptoJS OpenSSL string — wait: `Settings.vue:305` uses `:href="'data:image/png;base64,' + b64wallet"`, so the browser decodes the `data:...;base64,` URI on download and saves the raw `walletRecord.data` text to disk!).
  - Verify that `data` is either a valid `AWEv1.<iterations>.<salt>.<iv>.<ciphertext>` envelope or a valid legacy ciphertext, or cap its size.
  - Log out an already-open wallet before redirecting to `/accounts` (`ImportWallet.vue:113` pushes `/accounts`, which if another wallet is currently unlocked shows the *already-open* wallet's accounts rather than prompting to unlock the newly imported wallet).
- **Attacker precondition:** User imports a malformed/corrupted file, or imports a second wallet while a first wallet is already unlocked.
- **Impact:** Importing while another wallet is unlocked redirects to `/accounts` still showing the *previous* open wallet under its session while `lastUsedWallet` in `localStorage` is updated to the newly imported wallet's name — confusing the user about which wallet is active. Importing a corrupt or non-wallet file succeeds with no error until the user tries to open it (where it always reports "Wrong password").
- **Recommendation:** In `wallet/importWallet`, validate that `data` matches `AWEv1.<int>.<b64>.<b64>.<b64>` (or legacy `U2FsdGVkX1...` base64) with a reasonable size cap (e.g. 10 MB), and if `state.wallet.isOpen` is true, dispatch `wallet/logout` before returning so `/accounts` prompts the user to unlock the newly imported wallet.

### AW-2026-079 — `wallet/deleteAccount` matches by `name && addr`, leaving the account intact if `findIndex` returns `-1` (`splice(-1, 1)` deletes the last account in the wallet) — **Low** — New
- **Status:** New
- **Affected files:** `src/store/wallet.ts:557-562`, `src/pages/AccountOverview.vue:115-124`.
- **Description:** In `src/store/wallet.ts:557-562`:
  ```ts
  deleteAccount(state, { name, addr }: DeleteAccountPayload) {
    const index = state.privateAccounts.findIndex(
      (acc) => acc.name == name && acc.addr == addr
    );
    state.privateAccounts.splice(index, 1);
  }
  ```
  In JavaScript, `Array.prototype.splice(-1, 1)` removes the **last element** of the array! If `findIndex` returns `-1` (for example, if `name` is out of sync with `acc.name` after a cross-tab merge or rename, or if `deleteAccount` is called with a stale name), `splice(-1, 1)` silently deletes the **last account in `privateAccounts`** (including its private key / mnemonic) and `deleteAccount` then persists that deletion via `saveWallet` (and since `addr` was in `knownAddresses`, the deleted last account is also in `knownAddresses`, so `mergePrivateAccounts` treats it as an intentional deletion in this tab and drops it from IndexedDB!).
- **Attacker precondition:** None (self-inflicted edge case when an account's `name` in the caller differs from `acc.name` in `state.privateAccounts`, or a race between rename and delete).
- **Impact:** Deleting an account whose `name` does not match `acc.name` deletes the **wrong** account (the last account in `state.privateAccounts`) and persists the removal of its secret key.
- **Recommendation:** Match by `acc.addr === addr` (addresses are unique identifiers; `name` is a mutable label) and guard `if (index === -1) return;` before calling `state.privateAccounts.splice(index, 1)`.
