## 3. Findings

### AW-2026-071 — Direct now signs contract create/update/delete; the review identifies code only by hash — **Medium** — New
- **Files:** `src/scripts/direct/protocol.ts` (`directUnsupportedReason`, appl branch), `src/scripts/direct/appCall.ts`, `src/components/DirectAppCard.vue`, `src/components/ConnectRequestsTable.vue` (`showAppCard`, `revealLifecycleFirst`, auto-expand watcher).
- **Description:** Commit `1eed6ae` lifts the earlier refusal of app creation and program updates. The popup shows the programs as size, SHA-256, program address and raw hex, with a warning, a create-with-extra-effect error, a "reveal first" gate and auto-expansion. It cannot show what the code does, and for an **update** it does not show or compare the program currently deployed, so the user cannot tell what changes. The args, accounts, foreign assets and boxes rows are still rendered for lifecycle transactions (checked: only the "app" and ARC-56 rows are hidden behind the card).
- **Attacker precondition:** A site the user has connected (or a look-alike origin the user connects) and a user who signs for an account that is creator/admin of a contract. No silent signing; the origin is browser-verified.
- **Impact:** An approved-looking request to `UpdateApplication`/`DeleteApplication` on an app the account controls replaces or destroys that contract's logic; for a protocol admin key this is a full takeover, for others loss of the app and its state. Limits already in place bound the surface: sender scope (4100), AVM size/page limits enforced before hashing, no program bytes on non-create/update calls, creations may not close out or clear state, unknown OnComplete refused, and unknown networks refuse all `appl`.
- **Recommendation:** Keep the card. Add (a) for an update/delete, the **current** on-chain approval/clear program hash from algod (flagged as node-supplied, AW-2026-010/011) so "unchanged" vs "different" is visible; (b) a one-line hint in the warning that the user should compare the hash with their own build output; (c) consider requiring the account to be explicitly granted to the site for lifecycle calls (per-request re-confirmation of the origin) when the grant was made long ago. Pin the reveal-first behaviour with an E2E negative (it exists in `direct-app-lifecycle.spec.ts`).

### AW-2026-072 — Direct sends a signed request to the site automatically after returning from the multisig signing page — **Informational** — New
- **Files:** `src/components/ConnectRequestsTable.vue` (`onMounted` auto-send), `src/pages/Sign.vue` (`retToWalletConnect` sets `direct/setReturnedFromSigning`), `src/store/direct.ts`.
- **Description:** After signing on `/payWC`, pressing "Return" sets `{at, txId}`; on mount the request table sends the request holding that transaction if everything is signed and the return was under 15 s ago. The flag is only set by that explicit click, matches by transaction id, expires, and is cleared on mismatch. I found no path where it fires unasked.
- **Residual:** `signer.signed` can still hold dApp-supplied pre-signed blobs (AW-2026-065 residual), so "fully signed" is not a statement that this wallet produced every signature. Impact is nil for the wallet's own funds.
- **Recommendation:** None required; consider also requiring the txId to be one this wallet actually signed in the session.

### AW-2026-073 — Cross-tab account merge lets the saving tab's copy win and can resurrect accounts when the persisted list is empty — **Low** — New
- **Files:** `src/scripts/walletPersist.ts:24-52` (`mergePrivateAccounts`), `src/store/wallet.ts` (`saveWallet`, `applyAccountMerge`, `knownAddresses`).
- **Description:** The AW-2026-059 fix correctly keeps accounts added by another tab and drops accounts it deleted. For an account present on both sides the saving tab's copy wins wholesale, so a stale tab overwrites newer metadata another tab wrote for the same account (name, hidden flag, cached `data`/rekey info, newly generated HD child fields). Dropping is only trusted when the persisted list is non-empty, so if every account was deleted in another tab, a stale tab re-adds them. `knownAddresses` is a module-level set reset only on logout/destroy.
- **Attacker precondition:** None; two tabs open on the same wallet and a stale one that saves.
- **Impact:** Low. Key material of an existing account is not changed by normal flows, and the failure direction (resurrecting an account) is the safe one for funds. A lost name/visibility change is a nuisance.
- **Recommendation:** Merge per account by a `modified` stamp or field-wise for the non-secret metadata; document the "empty persisted list" behaviour in `mergePrivateAccounts` and add a unit case.
