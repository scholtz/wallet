## 1. Executive summary

This is an incremental audit of `381ae2b..604098a` (9 commits, 33 files). Functionally the only security-relevant change is **Biatec Direct "sign on every network"** (`945d771`, `dc85762`): the popup no longer refuses a request for a network other than the wallet's selected one. Instead it works out which network the request names from the full 32-byte genesis hash, shows it in a prominent card (with a warning for networks it does not recognise), binds every transaction to that hash and to a consistent genesis ID, and selects rekey mappings from the verified network rather than from a dApp-supplied string. The rest of the range is a popup size/unlock-banner UI refresh and a CI step-order fix.

The design is sound, and no Critical or High finding was raised. Three new findings are recorded: **0 High, 1 Medium, 1 Low, 1 Informational**. The Medium finding (AW-2026-068) is a **regression of a documented Direct property**: a connection grant is no longer bound to the network it was made on. The stored `genesisHash` of a session is now never read, so a site approved on one chain can ask for signatures on any other chain, relying solely on the network card for the user to notice. The remaining effect of the change is reduced review fidelity on a foreign network (no ARC-56 decoding, no simulation, no asset names).

None of the nine open findings from the previous audit (AW-2026-059..067, including the High AW-2026-059 lost-update bug) was touched by this range; `src/store/wallet.ts`, `src/shared/wc.ts`, `src/shared/decodeSignRequests.ts`, `src/store/{wc,liquid}.ts`, `pages/Sign.vue` and `docker/default.conf` are byte-identical to the previously audited state, so all are carried forward unchanged. AW-2026-059 remains the highest-priority open item.

## 3. Findings

### AW-2026-068 — Direct grant is no longer bound to the network it was made on (documented property regressed) — **Medium** — New
- **Files:** `src/store/direct.ts:340-349` (sign_transactions: the removed `session.genesisHash !== check.normalized` comparison), `:456-466` (sign_data), `:556-576` (session still stores `genesisHash` but nothing reads it; confirmed by grep: no reader of `session.genesisHash` remains), `src/scripts/direct/sessions.ts:82` (field still required on parse), `docs/DIRECT.md`.
- **Description:** The previous audit recorded "grants network-bound" as a strength of the transport. Commit `945d771` deliberately removed that check so Direct signs on any chain. A connection approved for site S on one network (for example a testnet game) now lets S request signatures for the same accounts on mainnet; the only barrier is the new network card and the user's click on Sign. For sign_data, `genesisHash` is optional; when omitted no network is shown at all (a short "network not named" note appears) and the rekey env falls back to the wallet's selected network.
- **Attacker precondition:** The user connected a site (or a compromised/malicious dApp origin) that is approved for their accounts, then opens a later request from it. The user must still unlock, read and press Sign; no silent signing.
- **Impact:** Weakens a user's mental model ("I authorised this site for testnet"). A malicious site that is trusted on a test network gets a clean path to ask for a mainnet payment. Transaction content is still fully displayed (payment/axfer summary, close-to/rekey warnings, sender scope 4100), so this is a trust-cue weakness, not a bypass.
- **Recommendation:** Keep the field meaningful: record the network in the grant and, when a later request names a different network, show an explicit "this site was connected on <X>, now asks for <Y>" interstitial (or require re-approval for `kind: "main"` when the grant was made on a `test`/`unknown` network). Remove the dead field only if the product decision is that grants are network-agnostic, and then update `docs/DIRECT.md`/registry text accordingly. Add an E2E for connect-on-testnet then sign-on-mainnet.

### AW-2026-069 — Reduced review fidelity on a foreign network (no ARC-56 decoding, simulation or asset names) — **Low** — New
- **Files:** `src/components/ConnectRequestsTable.vue` (`foreignNetwork`, `formatNative`, `formatAssetAmount`, `getAssetSync`, hidden `Arc56RiskIcon`/`Arc56RequestSummary`/`Arc56CallDetails`/`TransactionGroupSimulation`).
- **Description:** To avoid describing a Voi asset or app with the id of a mainnet one, all wallet-network enrichments are suppressed when the request is on a network other than the wallet's selected one. This is the right call for safety, but it means a foreign-network application call is shown as raw fields only, with amounts in "units" for networks without a known token, so the user is asked to sign with little context. `directUnsupportedReason` still restricts the signable kinds, which bounds the impact.
- **Impact:** Users may approve what they cannot meaningfully read; combined with AW-2026-068 this is the practical path to a confused sign. No bypass of any check.
- **Recommendation:** Keep the suppression. Show an explicit "details are unavailable for this network" banner on application calls (the current note is only in the expansion) and consider refusing `appl` transactions on `unknown` networks.

### AW-2026-070 — Direct popup self-resizes and moves for any opener, and the network table is a second hash list to maintain — **Informational** — New
- **Files:** `src/pages/Direct.vue` (`onMounted` → `resizeTo`/`moveTo`), `src/scripts/direct/windowSize.ts`, `src/scripts/direct/networks.ts:267-303` (`KNOWN_NETWORKS`).
- **Description:** The enlarge logic runs on mount for any window with a `window.opener`, before the dApp origin is verified. It is bounded to the available screen area and is a no-op for non-script-opened windows, so there is no security impact beyond window geometry manipulation by an arbitrary opener. Separately, the wallet-side hash table duplicates `@txnlab/use-wallet` and the adapter's `BIATEC_EXTRA_NETWORKS`; a wrong or stale entry would mislabel a chain. Spot-check of the six entries against published values found no discrepancy and the matching uses the full 32-byte hash (prefix matching was removed — good).
- **Recommendation:** Run the resize after the origin is verified; add a unit test that pins each entry against a literal hash so edits are intentional.
