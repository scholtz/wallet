## Executive summary

This audit covers the 21 commits on `master` since the prior report (`4cb0443..7564250`), dominated by a **new ARC-60 arbitrary-data signing feature** (`algo_signData` over WalletConnect), a substantial **DEX-aggregator rework** (Biatec Router combined-split routing, a new opt-in "stage" router, simulation-driven quote selection), a genesis-ID fix for custom networks, and session-timeout UX work.

The headline result is negative: this audit raises **one Critical and one High** finding, both of which are realistic paths to complete loss of an account's funds.

The Critical finding is not new code — it is a long-standing property of the swap feature that prior audits did not trace. All three DEX aggregators (Deflex, Folks, Biatec Router) take transactions handed back by a remote HTTP API, decode them, and sign them **directly with the account's raw private key**, with no validation of any field and no display of the transactions to the user. A malicious or compromised aggregator API can return a transaction carrying `closeRemainderTo` or `rekeyTo` and the wallet will sign and submit it silently. This completely bypasses the reviewed-signing pipeline (close-to and rekey warnings) that the AW-2026-001 remediation built for every other signing surface in the wallet.

The High finding is in the new ARC-60 code: its domain-binding check is self-referential. Both the claimed `domain` and the `authenticatorData` that is supposed to attest to it arrive inside the same DApp-controlled request, and are only checked against each other — never against the actual WalletConnect session peer. A malicious DApp can therefore obtain a valid ARC-60 AUTH signature binding **any domain it names**, which is precisely the attack the check's own source comment says it prevents.

**Counts this audit:** New: 1 Critical, 1 High, 1 Medium, 2 Low/Informational. No prior risk regressed; no prior open risk newly closed. The 2026-07-30 fix pass (AW-2026-039/-040/-041/-042) is now committed on `master` and independently re-verified. Open technical risks (excluding `Accepted` user-behavior rows): 20 including the new ones.

## Findings

### AW-2026-043 — DEX aggregator swaps blind-sign server-supplied transactions with the raw private key

- **Severity:** Critical
- **Status:** New (pre-existing code, not previously traced by an audit)
- **Affected files:**
  - [`src/scripts/aggregators/biatec.ts`](src/scripts/aggregators/biatec.ts) — `execute()` L152–L281, decode loop L226–L241, `tx.signTxn(senderSK)` L246
  - [`src/scripts/aggregators/folks.ts`](src/scripts/aggregators/folks.ts) — `execute()` L104–L127, `txn.signTxn(senderSK)` L123
  - [`src/scripts/aggregators/deflex.ts`](src/scripts/aggregators/deflex.ts) — `execute()` L109–L169, `algosdk.signTransaction(decoded, senderSK)` L136
  - [`src/scripts/aggregators/types.ts`](src/scripts/aggregators/types.ts) — `getSK` on `SwapContext`, L43

- **Description:** Every swap aggregator's `execute()` follows the same shape:

  1. Obtain the account's raw 64-byte secret key via `context.getSK({ addr })`.
  2. Fetch a set of base64 transactions from the aggregator's HTTP API (`txsToSign` for Biatec, `folksTxns` for Folks, `deflexTxs.txns` for Deflex).
  3. `algosdk.decodeUnsignedTransaction(...)` each one.
  4. Sign **all of them** with the raw `sk` and submit.

  Between steps 3 and 4 there is no validation of any kind. The wallet does not check that the transaction's `sender` is the user's own account, does not check `closeRemainderTo`, does not check `assetCloseTo`, does not check `rekeyTo`, does not check the receiver or amount against the quote the user was shown, and does not check `genesisID`/`genesisHash`. The transactions are never rendered to the user before signing — there is no `Sign.vue`-style review step, no confirmation dialog listing them, and none of the red close-to/rekey `Message` warnings that the AW-2026-001 remediation added to every other signing surface in the wallet. The user clicks one "Execute" button showing a quote figure, and an opaque set of remote-supplied transactions is signed with their key.

  This matters because it routes around the entire trust architecture the earlier audits built. `store/signer.ts` exists precisely so that signing is centralized and reviewable; `store/algod.ts`'s `assertParamsMatchNetwork` exists to cross-check genesis before building a transaction; `ConnectRequestsTable.vue` and `SignAll.vue` exist to show the user dangerous fields before they sign. The swap path uses none of them — it pulls the bare `sk` out of the wallet and calls `algosdk` directly.

  Biatec Router is first-party (operated by the same vendor as the wallet), which lowers the practical likelihood for that one aggregator but does not change the property: it is still a remote HTTP endpoint whose responses become signed transactions with no client-side check. Deflex and Folks are genuinely third-party. All three are reached over HTTPS, so a passive network attacker is not sufficient; the precondition is control of (or a compromise at) the aggregator API itself, or of its TLS/DNS/CDN path.

- **Attacker precondition:** Control of, or a compromise anywhere in the serving path of, `router.api.biatec.io`, `stage.router.api.biatec.io`, the Deflex API, or the Folks API — the same class of precondition as a malicious dependency. The user performs no unusual action: they open the swap page, request a quote, and click Execute, which is the feature working exactly as intended.

- **Impact:** Complete and immediate drain of the swapping account. A returned payment transaction with `closeRemainderTo` set to an attacker address empties the account's ALGO balance in a single transaction; an `assetCloseTo` does the same per ASA; a `rekeyTo` hands the attacker permanent signing authority over the account, surviving any subsequent password change or session logout, because the wallet's key material is no longer what controls the account. Because the transactions are signed and submitted in one click with no display, the user's first indication is the post-swap balance reload.

- **Recommendation:** In order of importance:
  1. **Validate before signing.** Before signing any aggregator-returned transaction, reject the whole group if any transaction has `closeRemainderTo`, `assetCloseTo`, or `rekeyTo` set, or has a `sender` that is not an account the user controls. These fields have no legitimate role in a swap route; a hard rejection costs nothing and closes the fund-loss path entirely. This is the single highest-value fix and is a small, self-contained change in each `execute()`.
  2. **Show the user what they are signing.** Route swap execution through the same review surface as other signing (or, at minimum, render the decoded transactions — sender, receiver, asset, amount, fee, and any dangerous field — in an expandable panel before the Execute button commits). The simulation panel added in AW-2026-039 is a preview of *outcome*; it is not a substitute for showing the *payload*.
  3. **Cross-check the economics.** Verify that the group's net effect on the user's account matches the quote that was displayed, within the configured slippage — the `receiveMinimum` value is currently sent to the router as a request parameter and trusted to have been honored, never verified client-side against the returned transactions.
  4. Longer term, consider whether the swap path needs the raw `sk` at all, or whether it can dispatch through `signer/signBySk` so that all signing in the app remains observable from one place.

### AW-2026-044 — ARC-60 domain binding is self-referential; a DApp can obtain an AUTH signature for any domain it names

- **Severity:** High
- **Status:** New
- **Affected files:**
  - [`src/scripts/encoding/arc60.ts`](src/scripts/encoding/arc60.ts) — `validateAuthenticatorDataDomain` L95–L102, `buildAuthenticatorData` L81–L88, `decodeArc60Request` L128–L152
  - [`src/store/wc.ts`](src/store/wc.ts) — `algo_signData` request handling L289–L344, `signSignDataItem` L678–L710
  - [`src/store/signer.ts`](src/store/signer.ts) — `signArc60Data` L431–L480
  - [`src/components/ConnectSignDataRequestsTable.vue`](src/components/ConnectSignDataRequestsTable.vue) — domain display and `domainValid` gating, L54, L66–L76

- **Description:** ARC-60's domain binding exists so that a signature a user produces for DApp A cannot be replayed as proof of authentication to DApp B. The implementation checks that the first 32 bytes of `authenticatorData` equal `SHA-256(domain)`:

  ```ts
  // arc60.ts L95-L102
  export async function validateAuthenticatorDataDomain(
    authenticatorData: Uint8Array, domain: string,
  ): Promise<boolean> {
    if (authenticatorData.length < 32) return false;
    const expected = await sha256(new TextEncoder().encode(domain));
    return bytesEqual(authenticatorData.slice(0, 32), expected);
  }
  ```

  Both inputs come from the same place: `decodeArc60Request` reads `item.domain` and `item.authenticatorData` out of the incoming WalletConnect request params (`request.params[0]`, `wc.ts` L290–L292), which are entirely under the requesting DApp's control. The check therefore only proves the DApp computed a hash correctly. It is trivially satisfied by any attacker: pick any target domain, compute `SHA-256(target) || 0x01`, and send it. `buildAuthenticatorData()` in the same file is a ready-made helper for doing exactly that.

  The source comment above the function states the intended property explicitly — *"so a malicious dApp cannot claim a different domain than it actually is"* — and the implementation does not achieve it. What is missing is a comparison against the **actual** origin of the request. That value is available: WalletConnect supplies session peer metadata (`session.peer.metadata.url`, already read at `wc.ts` L532–L537 for the active-sessions display) and a `verifyContext` origin-attestation signal, which the AW-2026-008 remediation already surfaces for *session proposals*. Neither is consulted on the `session_request` path, and `wc.ts` has no `verifyContext` handling there at all.

  The defense-in-depth layers do not compensate. `signer/signArc60Data` re-runs the same self-referential check (L432–L442) — the comment says it is duplicated there "so it can never be skipped regardless of call site," which is true but does not help, since the check itself is the problem. The UI in `ConnectSignDataRequestsTable.vue` shows `item.domain` to the user as a plain string and only raises `arc60.domain_mismatch` when the self-consistency check fails; because the attacker controls both halves it never fails, so the user is shown an attacker-chosen domain with no warning and nothing to compare it against — the session peer's real identity is not displayed alongside it in that table.

  Note also that the digest signed is `SHA-256(data) || SHA-256(authenticatorData)` (`computeArc60Digest`, L105–L115), containing no wallet- or protocol-level domain-separation tag; the only thing binding the signature to a domain is the `authenticatorData` half, which is the value this finding shows to be unauthenticated.

- **Attacker precondition:** A malicious DApp with an approved WalletConnect session (which the user grants, and which now includes `algo_signData` — `wc.ts` L512), and a user who approves one sign-data request on that DApp. No unusual user action beyond normal use of a sign-in-with-wallet flow, since the request looks legitimate and the displayed domain is whatever the attacker chose.

- **Impact:** The attacker obtains a valid ed25519 signature, from the user's real account, over an ARC-60 AUTH digest that attests to a domain of the attacker's choosing. Any relying party that implements ARC-60 authentication and accepts that signature as proof of possession will authenticate the attacker as the user. This is account takeover on third-party services rather than direct on-chain fund loss, which is why it is rated High rather than Critical; the ceiling is set by how much those third-party services are worth. It is rated High rather than Medium because there is a concrete, cheap exploitation path today (not merely a weakened property), and because the entire security purpose of the feature's validation step is defeated.

- **Recommendation:**
  1. Cross-check `item.domain` against the actual session origin before signing: compare it to the hostname of `session.peer.metadata.url` for the topic the request arrived on, and refuse to sign on mismatch. Do this in `signer/signArc60Data` (the choke point that cannot be bypassed), not only in `wc.ts`.
  2. Consume WalletConnect's `verifyContext` on the `session_request` path as well as on session proposals, and treat `INVALID`/`SCAM` verification as a hard refusal for sign-data rather than a badge.
  3. In `ConnectSignDataRequestsTable.vue`, display the session peer's real name and URL directly beside the requested `domain`, so the user has something to compare against. A domain string shown with no provenance reads as verified when it is not.
  4. Reconsider the `arc60.domain_mismatch` copy: as written it implies to the user that a passing check means the domain was verified.

### AW-2026-045 — Biatec swap re-fetches a fresh route at execute time, so the simulated preview does not cover the bytes actually signed

- **Severity:** Medium
- **Status:** New (compounds AW-2026-039)
- **Affected files:**
  - [`src/scripts/aggregators/biatec.ts`](src/scripts/aggregators/biatec.ts) — `getQuote()` L93–L150 (`receiveMinimum: 0`, L117), `execute()` L152–L281 (second `postApiV1RouterRouteTxs` call L202–L203, overwrite of `quotesKey` L210–L214)
  - [`src/composables/useSwap.ts`](src/composables/useSwap.ts) — `simulateAggregatorQuote` (runs only from `clickGetQuote`), `clickExecuteBiatec` / `clickExecuteBiatecStage`

- **Description:** The simulation-driven quote work added this cycle dry-runs each aggregator's prepared transactions and uses the ledger-computed result for both route selection and the on-screen quote/price figures (`getEffectiveQuoteAmount`, `simulate.ts`). For Deflex and Folks this is coherent: the transactions simulated at quote time are the same objects later signed in `execute()`.

  Biatec is different. `getQuote()` calls `postApiV1RouterRouteTxs` with `receiveMinimum: 0` and stores the resulting route; `simulateAggregatorQuote` then simulates *those* transactions and the user sees the result. But `execute()` calls `postApiV1RouterRouteTxs` **again** — a fresh request, with the real `receiveMinimum` computed from slippage — then overwrites `aggregatorData[quotesKey]` with the new response and signs the transactions from *that* response. No simulation is run against the second response, and the displayed figures are not recomputed from it before signing.

  So the preview the user reviewed and the payload they authorize come from two different API responses, issued at different times, with different request parameters. Even with a fully honest router the two can legitimately diverge (pool state moves between the calls). With a dishonest one, the divergence is chosen by the server: it can return a benign route to the simulate-and-display call and a hostile one to the execute call, and the preview will have shown clean. That makes the simulation panel — whose copy AW-2026-039 already had to soften — actively misleading on this path rather than merely optimistic.

  This is a Medium in its own right and not folded into AW-2026-043 because it is a distinct defect: even after AW-2026-043's validation is added, a preview that describes different bytes than the ones being signed is a UI-trust problem of the class the audit instructions call out in §1.9.

- **Attacker precondition:** For the *misleading-preview* impact, control of the Biatec Router API (same precondition as AW-2026-043). For the benign-divergence impact, none — ordinary pool movement between the two calls is enough for the executed swap to differ from the previewed one.

- **Impact:** The user's informed consent is based on a simulation of transactions that are not the transactions signed. Combined with AW-2026-043 (no validation, no payload display), the simulation panel is the only thing standing between the user and the router's response on this path, and it does not describe that response.

- **Recommendation:** Either (a) reuse the transactions already fetched and simulated at quote time rather than re-fetching in `execute()` — requesting the correct `receiveMinimum` during `getQuote()` so one response serves both — or (b) re-run `simulateAggregatorQuote` against the freshly fetched route inside `execute()` and require the user to confirm the updated figures before signing. Option (a) is preferable: it removes the divergence rather than reporting it. Whichever is chosen, the swap should abort if the executed route's simulated output falls below the slippage-adjusted minimum the user was shown.

### AW-2026-046 — ARC-60 signing is not scoped to the WalletConnect session's approved accounts

- **Severity:** Low
- **Status:** New (related to AW-2026-016)
- **Affected files:**
  - [`src/store/signer.ts`](src/store/signer.ts) — `signArc60Data` L431–L480, `ensureAccount` L104–L116
  - [`src/store/wc.ts`](src/store/wc.ts) — `signSignDataItem` L678–L710

- **Description:** The `signer` address on an incoming `algo_signData` item is DApp-supplied. `signArc60Data` resolves it through `ensureAccount`, which searches the user's entire `privateAccounts` list — not the set of accounts approved for the WalletConnect session the request arrived on. A DApp granted a session for account A can therefore request an ARC-60 signature from account B and receive one, provided the user clicks Sign.

  This mirrors the existing behavior of the `algo_signTxn` path and the already-open AW-2026-016 (session namespaces are not enforced per-request), so it is a consistent gap rather than a new class of problem, and it is rated Low on that basis: the signer address *is* displayed in the request table via `AlgorandAddress`, giving an attentive user a chance to notice. It is recorded separately because the ARC-60 path is new code where the scoping check could have been added at the outset, and because it amplifies AW-2026-044 — an attacker who can both choose the domain and choose the account has a materially better position than one who can only choose the domain.

- **Attacker precondition:** An approved WalletConnect session for any one account, plus a user who approves a sign-data request without checking the displayed signer address against the account they believe they are using.

- **Impact:** An ARC-60 AUTH signature from an account the DApp was never granted access to. No direct fund movement.

- **Recommendation:** In `signSignDataItem`, resolve the session for `request.topic` and reject any item whose `signer` is not among that session's approved `algorand` namespace accounts. Apply the same check to `algo_signTxn` while there, which would also close AW-2026-016.

### AW-2026-047 — ARC-60 digest carries no protocol domain-separation tag

- **Severity:** Informational
- **Status:** New — **needs verification** against the final ARC-60 specification
- **Affected files:** [`src/scripts/encoding/arc60.ts`](src/scripts/encoding/arc60.ts) — `computeArc60Digest` L105–L115, `signArc60DigestWithSk` L154–L156

- **Description:** `computeArc60Digest` produces exactly `SHA-256(data) || SHA-256(authenticatorData)` — 64 bytes with no constant prefix identifying it as an ARC-60 AUTH digest — and `signArc60DigestWithSk` signs it with `nacl.sign.detached` using the same ed25519 key that signs Algorand transactions. Algorand transaction signing prefixes its payload with the `TX` tag, so the two payload spaces do not collide structurally today, and forcing a 64-byte digest to also be a valid `TX`-prefixed msgpack transaction would require a second-preimage attack on SHA-256 (infeasible). The practical risk today is therefore nil, and this is recorded as Informational rather than Low.

  It is recorded at all because the separation rests entirely on hash preimage resistance rather than on structure, and because the same key is now used across two signing protocols where it previously served one. Any future third payload format signed by this key should be checked against both.

  I have not verified against the published ARC-60 text whether this digest construction is mandated as-is; if it is, the correct response is to note the property rather than deviate from the spec. Flagged per instructions §2.6 rather than asserted as a defect.

- **Attacker precondition:** None known.
- **Impact:** None known today.
- **Recommendation:** Confirm the digest construction against the final ARC-60 specification. If the ARC leaves it open, prefix the digest with a constant domain-separation tag. Regardless, document in `CLAUDE.md` that the account ed25519 key now signs two distinct payload formats, so a future third format is evaluated against both.

Note that `algosdk` already bundles its own ed25519 implementation, so the app now has two — not a defect, but worth knowing.
